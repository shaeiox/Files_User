No Graphify relationship has been invented.## Goals / Non-Goals**Goals:**- Make the existing Browse icon an interactive target that reaches the **same destination** as the item's  existing name link, for both directories and files.- Remove the extra right-side File Action control for directories only, keeping directory navigation  fully available.- Preserve the file-side Download action, the name link, the router, and `ResourceService` unchanged.- Keep the dedicated File Actions module boundary intact: the module owns dedicated File Actions only.- Keep the row's existing six-child structure and every index-sensitive column rule valid.- Accessibility for the newly interactive icon: accessible name, keyboard operability, visible focus, no  redundant tab stop.- Incremental delivery: every phase is independently verifiable and leaves the app working.**Non-Goals:**- Changing the name link's target, role, or accessible name.- Making rows clickable.- Modifying `router.js`, `resource-service.js`, backend `lib/*`, `home.css`, or Home page behavior.- A generic command/menu/toolbar/action framework, action palettes, or context menus.- Implementing future actions (Preview, Copy Link, Rename, Delete, Share).- Introducing a test framework or CI.- Changing the icon artwork, the badge column, or the header labels.- Fixing pre-existing quirks unrelated to this change (the `browse.html` legacy shell).## The two target categoriesThis change distinguishes two clearly separate kinds of interactive target in a Browse row. Conflatingthem is the source of the contradiction being fixed, so the separation is stated explicitly.```┌─ Row ───────────────────────────────────────────────────────────────────┐│ 1. PRIMARY BROWSE NAVIGATION TARGET                                      ││    ├─ Browse icon  (BrowsePage-owned, becomes interactive)               ││    └─ Name link    (BrowsePage-owned, unchanged)                         ││    → BOTH resolve to the SAME destination/action for the item            ││    → directory: SPA navigation   |  file: download (+ data-file)         ││    → ALWAYS PRESENT, for every item                                    ││                                                                          ││ 2. DEDICATED FILE ACTION                                                 ││    └─ FileActions module output, rightmost column, child 6               ││    → Download, file items only                                          ││    → ABSENT for directories                                             │└──────────────────────────────────────────────────────────────────────────┘```**Why the Browse icon needs to become an additional target.** Before this change, a directory row's onlynavigation affordances were its name link and a non-interactive decorative icon, while a file rowadditionally had a Download action. That asymmetry meant directories were under-served: the one thing auser does most with a folder (open it) required hitting a small text target, while the row's most visuallyprominent element (the icon) did nothing. Making the icon a real target for the same destination:1. gives a large, comfortable hit target for the most common action, without removing the name link;2. lets the redundant directory-specific Open action be removed, so a directory row carries exactly one   navigation affordance (the primary target, exposed twice) instead of two semantically identical ones;3. keeps the row's identity element (the file/folder icon) meaningful instead of decorative.**Why the directory-specific extra action is removed.** The `open` action was a second control pointing atexactly the same destination as the name link. With the icon now serving as the primary alternativetarget, the `open` control is pure redundancy: it duplicates a destination, adds a secondaction-shaped affordance to every directory row, and forces hover-reveal/accessible-name/tab-stop work tobe maintained for no navigational gain. Directory navigation is not lost — it is retained in two places(name link and icon).## Goals reconciled with existing architecture| Concern | Owner | Change ||---|---|---|| Row structure, icon markup, name link, type/modified/size cells, header row | `browse.js` (BrowsePage) | Icon cell becomes interactive || Dedicated File Action definitions, applicability, rendering | `assets/js/file-actions.js` (FileActions) | `open` definition removed; `download` retained || Action-specific labels, action URLs, action SVG, action attributes, action a11y | `assets/js/file-actions.js` (FileActions) | **No change — already fully owned (D11)** || Primary icon target, its label verb, its artwork, `linkAttr`/`href` | `browse.js` (BrowsePage) | **Never moves — not a File Action (D1, D4, D11)** || Generic helpers (`escapeHtml`) and shared i18n keys | each module / `i18n.js` | **Not relocated — out of scope (D11)** || URL primitives (`browseHref`, `downloadHref`, `listFiles`) | `assets/js/services/resource-service.js` | Unchanged, still the only source of target URLs || SPA navigation, link interception, `data-file` contract | `assets/js/router.js` | Unchanged || Row and action-area styles | `assets/css/browse.css` | Icon anchor styles added; action-track width pinned in both templates; no track-count, track-order, or `nth-child` change || Action/name labels | `assets/js/i18n.js` | Unchanged; existing `btnOpen` / `btnDownload` reused |No new module, no new file, no new generic action abstraction is introduced.## Decisions### D1. The primary Browse icon target lives in BrowsePage, not in FileActions**Decision:** the icon anchor is produced inside `renderFilesList()` in `browse.js`, next to the existingname link, reusing the exact same `href` variable and the same `linkAttr` decision the name link alreadyuses.Rationale:- The icon is a *navigation* concern about the item, structurally identical to the name link. FileActions  owns *dedicated File Actions* only; putting the icon in the module would (a) blur the boundary the  module exists to create, and (b) make BrowsePage's most basic row element depend on a second module.- The single existing `href` variable (`browse.js:360-362`) already encodes the type-derived choice.  Reusing it means the icon target and the name link **cannot diverge** — there is no second  type-branching site to keep in sync.- `ResourceService` remains the only URL source; no new URL construction.Rejected alternative: extend `FileActions` with an `iconTarget()` entry point. Rejected — it would makethe "dedicated File Actions" module own primary navigation, contradicting the module's purpose and the"minimal module surface" requirement.### D2. The icon anchor is nested **inside** the existing `.f-icon` cell, not substituted for it**Decision:** child 1 remains `<div class="f-icon f-icon-dir|f-icon-file">` and the anchor is placed*inside* it, sized to fill the cell.Rationale (evidence-based, not cosmetic):- `.f-icon` is a positioned, sized, themed box: 32px flex box with background/border/radius  (`browse.css:208-217`), plus a 40px variant and `margin-bottom` in grid mode  (`browse.css:399-403`), plus dark-theme overrides (`browse.css:231-241`).- **Grid-index safety.** Children 3-5 are styled and hidden via `nth-child(3|4|5)`  (`browse.css:199-206`, `:431-435`, `:470-474`). If the icon cell were *replaced* by two sibling  elements (or by an anchor that also carried a wrapper), every subsequent child would shift by one and  the type/modified/size rules would be applied to the wrong columns — silently, with no error. Keeping  exactly one child in position 1 makes that failure structurally impossible.- Keeping `.f-icon` means all existing icon styling, theming, and the grid-mode size rule continue to  apply unchanged; only a small anchor-level rule (fill the box, center content, no underline, inherit  color) is needed.- Accessibility-wise this also keeps the icon's decorative artwork (`.f-icon` background/border) out of  the link's accessible name, with the SVG marked `aria-hidden`.Rejected alternative: make the `<a>` itself carry `class="f-icon"`. Rejected — it removes the `div`child, changing the child count and the `.f-icon` flex box contract, and it forces hover/activebackground rules to be re-specified for the link element.### D3. Two sibling anchors, not one merged anchor**Decision:** the row exposes **two separate anchors** for the primary target — the icon anchor (child 1)and the name link (child 2) — never nested in one another.Rationale:- Confirmed requirement 3 states the icon is an *additional* target that "does not replace the name  link". Two targets are the specified behavior; a single merged anchor would collapse them into one  control and change the name link's structure and semantics.- A single anchor wrapping icon + name would also change what the name link is (its element, class hook  `.f-link`, and truncation rules in `browse.css:252-266` and `:412-429` all assume the anchor is the  text element), and would make the icon's contribution to the accessible name depend on the name text  rather than on an explicit action label.Cost, stated honestly: two anchors means two tab stops for one destination. This is **not** a redundantstop — it is the specified two-target behavior. The spec therefore forbids a *redundant* stop (an extraactivatable wrapper or duplicate control) rather than forbidding the second stop. Ordering is deterministicand matches the visual order: icon → name → File Action, in both list view (left-to-right grid) and gridview (top-to-bottom flex column), so tab order is never surprising.Rejected alternative: one anchor wrapping icon + name. Rejected — conflicts with confirmed requirement 3and rewrites existing name-link structure/styles.### D4. The icon target's accessible name is an action label, distinct from the name link's**Decision:** the icon anchor exposes `aria-label` (and `title`) of the form`"{verb} {item name}"` — `btnOpen` for directories, `btnDownload` for files — reusing the **existing**i18n keys (`i18n.js:68`, `:67` and their fa counterparts), and the icon SVG gains `aria-hidden="true"`.Rationale:- Two links to the same destination that announce identically ("el9", "el9") are indistinguishable in a  screen-reader link list. The action label resolves that at zero i18n cost, and it reuses keys that  already exist in both locales.- The name link's accessible name is untouched (it remains the item name), satisfying "Name link  accessible name unchanged".- `aria-hidden` on the SVG is required: `svgIcon()` currently emits no such attribute  (`browse.js:548-552`), so the raw `<svg>` would otherwise contribute noise to the link's name.Note on label reuse: the verb choice for the icon deliberately reuses `btnOpen` / `btnDownload` ratherthan introducing new keys such as `btnOpenFolder` — the verbs are the same user-facing actions, andadding keys would duplicate the dictionary without changing meaning. Because the label is built in`browse.js` from the same `d` dictionary already passed to `renderFilesList()`, no new i18n key, no`data-i18n` conversion, and no `applyLang()` change is required (labels are produced at render time,exactly like every other label in the row).Rejected alternative: export a shared `labelFor(item, d)` helper from FileActions for BrowsePage to call.Rejected — it would couple primary navigation back to the File Actions module (D1) to avoid a singleone-line expression.### D5. `FileActions.render()` keeps returning the container for every item; only its *controls* change**Decision:** the module continues to emit the `<div class="f-actions">` container on every row. Fordirectory items it emits **no control** inside it. The `open` action definition is removed from themodule's action list; `download` remains, still gated on `type === "file"`.Rationale:- **Module boundary.** If `browse.js` decided whether to call `FileActions.render()` per item type,  applicability knowledge would leak into BrowsePage and break the "single call point" and  "BrowsePage responsibilities remain unchanged" requirements. Keeping the call unconditional keeps  applicability inside the module.- **Layout invariant — CORRECTED after browser measurement (see R16 and D11a).** This bullet previously  claimed that because skeleton rows (`browse.js:567-573`) emit only five children and directory rows emit  an empty `.f-actions`, "the `auto` sixth track simply collapses to zero width … the directory-action  removal is layout-safe". **That reasoning is falsified and is withdrawn.** It proved only that such a row  *renders*, not that its *columns align*:  - Every `.trow` is an **independent grid container** (`browse.css:168-169`); `thead` and each data row    are separate containers, so grid tracks are **not shared** between them.  - The sixth track was `auto`, i.e. **content-derived per row**: directory rows resolve it to `0px`    (empty `.f-actions`), file rows to `26px` (one `.f-action`), `thead` to `0px` (empty trailing cell).  - The only flexible track is track 2 (`minmax(0, 1fr)`), so it absorbed the entire 26px difference and    the **fixed** tracks 3/4/5 (90/160/90) started 26px earlier on file rows.  - Measured at 1440px: `thead` and directory rows resolved `40px 910px 90px 160px 90px 0px`, file rows    `40px 884px 90px 160px 90px 26px`; cell x-offsets differed by exactly **26px on cells 3-6 and 0px on    cells 1-2**, at every viewport from 320px to 1600px.  - **The fifth-child skeleton "proof" is retracted as layout-safety evidence.** It remains true that a    five-child row renders without error; it does not establish column alignment.  The corrected invariant: an empty-or-absent action cell is layout-safe only if the action track's width  is **content-independent**. It is now fixed (D11a). With the track pinned, `thead`, directory rows, and  file rows all resolve identical geometry (`40px 884px 90px 160px 90px 26px` at 1440px) and all three  pairings measure `[0,0,0,0,0,0]`. Keeping the empty container remains correct — it preserves the module  boundary and the uniform six-child invariant — but that is now justified by the *pinned track*, not by  an `auto` track collapsing.- **No new abstraction.** The `ACTIONS` array shape (`{ id, appliesTo, render }`) is unchanged, so  re-adding a directory-scoped action later is a single entry (see the spec's "Directory-scoped actions  remain re-addable").- `btnOpen` is not orphaned by removing the `open` action: it is reused for the directory icon label  (D4).Rejected alternative: have `render()` return an empty string for directories so no container is emitted.Rejected — it would make the row's child count type-dependent, weakening the uniform six-child invariantthat the `nth-child` rules and the header alignment rely on, for no observable benefit.### D6. Removal of the `open` action definition, not just its suppression**Decision:** delete the `open` entry from `ACTIONS` in `file-actions.js`.Rationale: leaving it would be unreachable code with an `appliesTo` predicate that can never fire, plusan unused SVG path and an unused `browseHref` call site. The applicability mechanism it demonstrates isstill present via `download.appliesTo`, so nothing is lost structurally. This is the only edit`file-actions.js` receives.### D7. No `stopPropagation()` / `preventDefault()` in the Browse row**Decision:** the implementation adds no event listeners, no `preventDefault()`, and no`stopPropagation()` for the icon target or the remaining File Action.Rationale (evidence-based):- Rows have **no** click handlers — `bindEvents()` binds only search, dropdown, and view-toggle controls  (`browse.js:391-462`); there is no ancestor handler that a bubbling click could trip.- The router's document-level interceptor resolves a single target with `e.target.closest("a[href]")`  (`router.js:115`). With sibling anchors, `closest` returns exactly the anchor under the pointer — never  two. So one click yields exactly one `navigate()`.- The icon SVG is `aria-hidden` and non-interactive, so `e.target` may be the `<path>` inside the SVG —  `closest("a[href]")` still resolves to the enclosing icon anchor. This is why no handler is needed on  the SVG itself.- Document-level listeners in `browse.js`/`i18n.js` that also see the click only close open dropdowns —  idempotent and already the case for name-link clicks today.This is recorded as a constraint, not a prohibition-with-holes: the spec requires the *observable*outcome (exactly one navigation/download) and forbids cancellation added without a demonstratedconflicting handler.### D8. `data-file` on every file target is mandatory, not conventional**Decision:** the icon anchor for a file item carries `data-file="true"`, produced from the **same**`linkAttr` string the name link already uses (`browse.js:368`).Rationale — this is the highest-severity correctness constraint in the change:- The router skips interception for `link.hasAttribute("data-file")` **or** `fileExtensions.test(href)`  (`router.js:124-126`), where the denylist is a fixed end-anchored extension list  (`router.js:9`).- `ResourceService.downloadHref()` returns `/api/download/<encoded relPath>` (`resource-service.js:27-29`).  For `notes.iso` the denylist happens to match. For `disk.bin`, `archive.7z`, or `blob.dat` it does not.  Without `data-file`, the router would `preventDefault()` and call `navigate("/api/download/…")`;  `resolveRoute()` returns `null` for that path, so the router would execute  `window.location.replace("/404.html")` (`router.js:32-36`) — the download silently becomes a 404 page.- Therefore a file icon anchor built from the same `linkAttr` is correct by construction: there is no  path by which the icon is built without `data-file`.- Symmetrically, directory targets are structurally immune to the extension denylist because  `browseHref()` always emits a trailing slash (`resource-service.js:22-25`) while the denylist is  end-anchored — this retires the previously recorded risk R5 (see §0).### D9. It is not: because each `.trow` is  an independent grid container and track 2 is the only flexible track, an `auto` action track makes  track 2 the shock absorber and displaces the fixed columns 3-5 by exactly the action width. See D5's  corrected invariant and R16.- A **fixed** track was chosen over `minmax(26px, auto)` on measured evidence:  - `minmax(26px, auto)` aligns correctly today, but the max stays content-derived, so adding a second    file-only action re-introduces the identical misalignment (measured: 28px). Verified: cards remain 184×160 and action positions are unchanged.- Hover/focus emphasis on the icon anchor must not change the box's size or position (no layout shift),  and must not repaint `.f-icon`'s themed background in a way that changes the row's visual weight;  color/opacity-level emphasis on the SVG stroke is the low-risk choice.- `:focus-visible` from `base.css:256-259` already applies to the anchor; the implementation must not  suppress it.
