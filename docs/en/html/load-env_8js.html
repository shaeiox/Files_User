Detailed Description

The environment bootstrap of the CloudAvid File Portal: reads the project-root .env file into process.env at boot — preferring the dotenv package, silently falling back to a hand-rolled parser — so that server.js's PORT and lib/files-service.js's FILES_ROOT are real before a single request arrives.

📖 Overview

🧒 ELI5 Summary

Imagine the portal is a restaurant that opens every morning. Before the first customer walks in, someone has to read the day's instruction sheet taped to the back door: "we open at port 3000, the food is stored in the warehouse behind the building". That instruction sheet is the .env file, and this file is the person who reads it out loud first thing in the morning.

The reader is also very polite. There are two ways the sheet can be read: the fancy way (a professional reader the restaurant hired — the dotenv package) and, if that employee didn't show up, a simple way (the manager reads it by hand — the small parser in this file). And the reader never shouts over someone who already knows the answer: if the boss already wrote the opening time on a sticky note (a real environment variable set by the operating system or Docker), the reader does not replace it with what the sheet says. The sheet is only for things nobody has mentioned yet.

If the sheet is missing or torn, the reader doesn't panic and doesn't close the restaurant — they just quietly start work with whatever they remember, and the doorman (server.js) picks a default door number (3000) while the kitchen keeps asking "where is the warehouse?" (which later becomes the 503 FILES_ROOT_MISSING answer from lib/files-service.js).

Core Responsibilities

  • One-Shot Bootstrap: loadEnv(projectRoot) is called exactly once, synchronously, at the top level of server.js, before lib/files-service.js is even required. It populates process.env for the whole Node process.
  • Preferred Path — dotenv: Tries require("dotenv").config({ path: envPath }) first. dotenv is a declared dependency in package.json ("dotenv": "^16.4.7"), so in a normal install this is the path taken.
  • Fallback Path — Hand-Rolled Parser: If dotenv cannot be loaded, a self-contained parseEnvText() performs a minimal KEY=VALUE parse so the server still boots with a broken/absent node_modules.
  • Never-Override Policy: Both paths only write a variable when it is currently null, undefined or "" — real environment variables (Docker, systemd, CI) always win over .env.
  • Never-Throw Contract: loadEnv() catches every failure and degrades to a console.warn at worst. Boot never crashes because of a bad .env.
  • Windows/Linux Robustness: The parser splits on /\r?\n/, so .env files edited on Windows (CRLF) and Linux (LF) both parse correctly.

🧭 Role in the Overall Architecture

This file is the first rung of the back-end's dependency ladder. The boot order in server.js is load-bearing:

  • server.js computes PROJECT_ROOT = __dirname and calls loadEnv(PROJECT_ROOT) at module top level.
  • Only then does server.js read process.env.PORT || 3000 and require ./lib/files-service.
  • lib/files-service.js reads process.env.FILES_ROOT lazily inside every request (resolveConfiguredRoot()), which is why it is also safe.

Upward, this module is consumed by exactly one file: server.js (const { loadEnv } = require("./lib/load-env");). Downward, it depends on two Node built-ins (fs, path), the optional dotenv package, and the .env file itself (documented by .env.example). It has no knowledge of HTTP, the download tree, or the frontend.

Note
What This File Does NOT Do:
  • It does not validate values. PORT=banana is loaded verbatim; the consequences surface later in server.js (listen failure) or nowhere. FILES_ROOT validation (exists? is a directory? has categories?) belongs entirely to lib/files-service.js.
  • It does not support dotenv's richer syntax: no export KEY=VALUE prefix, no multi-line values, no ${VAR} interpolation, no inline comment stripping (PORT=3000 # comment keeps # comment in the value on the fallback path). Those are dotenv-only conveniences.
  • It does not log success. A successful load is completely silent; only a failed fallback read produces output (console.warn).
  • It does not watch or reload .env. It runs once at module-load time; editing .env requires a server restart.
  • It does not protect itself over HTTP. server.js's security blocklist (pathname === "/.env" || pathname.startsWith("/lib/") || ... → 403) is what stops anyone downloading this module or the real .env over the network — a job that lives in server.js, not here.

Block: parseEnvText(text) — The Fallback Parser

  • 🎯 Purpose: A miniature .env parser used only when dotenv cannot be required. It converts raw file text into process.env writes with just enough syntax support to handle the keys this project actually uses (PORT, FILES_ROOT — see .env.example), including quoted Windows paths like FILES_ROOT="D:\CloudAvid\Downloads".
  • 🧒 ELI5: When the professional reader is absent, the manager reads the sheet line by line: skip the blank lines and the lines that start with # (those are doodles, not instructions), find the = sign, and read the left side as the label and the right side as the value — politely removing quotation marks if the value wears a coat. And the golden rule: never say anything someone has already said.
  • ⚙️ How It Works (Step-by-Step):
    1. Split: text.split(/\r?\n/) breaks the file into lines while swallowing the \r of Windows CRLF endings — essential because this repository is edited on Windows (server.js is CRLF) and deployed on Linux.
    2. Trim: each raw line is trim()-ed, so leading/trailing spaces around keys, values and separators are tolerated.
    3. Skip: if (!line || line.startsWith("#")) continue; — empty lines and full-line comments are ignored. (Inline trailing comments are not stripped; see the Note below.)
    4. Separate: const eq = line.indexOf("="); finds the first =. if (eq <= 0) continue; rejects both lines with no = (eq === -1) and lines where = is the first character (eq === 0, i.e. an empty key). A value that itself contains = survives intact, because only the first occurrence splits.
    5. Key/Value: key = line.slice(0, eq).trim(), value = line.slice(eq + 1).trim().
    6. Unquote: if the value both starts and ends with " (or both with '), the outer quote pair is sliced off (value = value.slice(1, -1)). The length-≥-2 requirement is implicitly guaranteed: a string that starts and ends with the same character has at least that length. Only symmetric pairs are stripped; "value' is left untouched.
    7. Non-Override Write: the guard if (process.env[key] == null || process.env[key] === "") uses loose == null (catches both undefined and null) plus the empty-string case, then writes process.env[key] = value. A variable set by the OS, Docker or CI always wins over the .env value — the same non-override semantics dotenv uses by default.
    8. No return value: the function communicates exclusively through the side effect on process.env — it returns undefined.
  • 📥 Inputs: text — the full UTF-8 contents of .env as a string.
  • 📤 Outputs: Mutates process.env (adds keys only when unset/empty); returns undefined. Throws nothing for malformed lines (they are silently skipped), so one bad line never blocks the others.
  • 🔗 Project Dependencies:
    • Depends on: nothing but the global process object — no fs, no path, no dotenv.
    • Consumed by: loadEnv only. It is deliberately not exported (see the exports block), keeping the module's public surface at exactly one function.
    • See also
      .env.example — the two keys it must understand (PORT, FILES_ROOT), including the quoted-Windows-path case.
    • See also
      lib/files-service.js — resolveConfiguredRoot() later consumes process.env.FILES_ROOT, whatever parser wrote it.
  • ⚠️ Breaking Change Warning: This function is the fallback of the fallback, which makes it the easiest place to introduce silent misconfiguration:
    • Removing the == null || === "" guard makes .env override real environment variables — in Docker/systemd deployments that export PORT/FILES_ROOT, the containerised values would be silently clobbered by a stale .env committed to the image.
    • Removing the startsWith("#") skip turns comment lines into garbage keys (they fail the eq <= 0 test only when they contain no = — a comment containing = would create a bogus variable).
    • Loosening eq <= 0 to eq === -1 would accept =value lines and create empty-string keys in process.env.
    • Changing the regex to split("\n") breaks Windows-authored .env files: every value would gain a trailing \r, and FILES_ROOT=D:\CloudAvid\Downloads\r resolves to a directory that does not exist → every listing request 503s with FILES_ROOT_NOT_FOUND.
    • Adding inline-comment stripping changes values that legitimately contain # (e.g. passwords in quoted strings) — do not "fix" this without checking dotenv's exact semantics.

function parseEnvText(text) {
for (const rawLine of text.split(/\r?\n/)) {
const line = rawLine.trim();
if (!line || line.startsWith("#")) continue;
const eq = line.indexOf("=");
if (eq <= 0) continue;
const key = line.slice(0, eq).trim();
let value = line.slice(eq + 1).trim();
if (
(value.startsWith('"') && value.endsWith('"')) ||
(value.startsWith("'") && value.endsWith("'"))
) {
value = value.slice(1, -1);
}
if (process.env[key] == null || process.env[key] === "") {
process.env[key] = value;
}
}
}
Note
The parser handles the syntax this project needs, not the full dotenv grammar. Unsupported (dotenv-only) constructs on the fallback path: export KEY=VALUE (key becomes export KEY), multi-line values, ${VAR} interpolation, and inline trailing comments. If a deployment relies on any of these, ensure node_modules/dotenv is actually installed (it is declared in package.json, so a plain npm ci guarantees it).

Block: loadEnv(projectRoot) — The Orchestrator

  • 🎯 Purpose: The module's entire public API. Loads <projectRoot>/.env into process.env once, preferring dotenv, degrading gracefully, and never throwing.
  • 🧒 ELI5: The morning routine: find the instruction sheet on the back door, call the professional reader if they showed up today, otherwise read it yourself, and if the sheet is missing or torn, just shrug and start the day anyway.
  • ⚙️ How It Works (Step-by-Step):
    1. const envPath = path.join(projectRoot, ".env"); — resolves the absolute .env path from the caller-supplied root. server.js passes PROJECT_ROOT (= __dirname), so in production this is <repo>/.env, exactly where .env.example says to create it.
    2. Preferred path: inside a try, require("dotenv").config({ path: envPath }); — dotenv reads and populates process.env (non-overriding by default) and the function immediately returns. Using require inside the function (instead of at the top of the file) is what makes dotenv optional: the require itself is the availability test.
    3. Fallback trigger: the bare catch { /* dotenv not installed — parse .env manually *\/ } swallows any failure from step 2 — module-not-found, a corrupted dotenv install, or a config error — and falls through. The comment documents the expected cause.
    4. Fallback path: if (fs.existsSync(envPath)) guards parseEnvText(fs.readFileSync(envPath, "utf8"));. existsSync keeps a missing .env completely silent (a legal state: real env vars may be provided by the platform); only an actual read/parse failure reaches step 5.
    5. Last-resort logging: the outer catch (err) around the fallback prints console.warn("Could not read .env:", err.message) and returns. The server still boots; PORT falls back to 3000 in server.js, and a missing FILES_ROOT surfaces later as the structured 503 FILES_ROOT_MISSING error from lib/files-service.js's resolveConfiguredRoot() — with a message that even tells the operator to "Add it to your .env file".
    6. Return value: undefined on every path. All communication is via process.env and (worst case) the warn line. This is what lets server.js call it bare at top level with no error handling.
  • 📥 Inputs:
    • projectRoot — absolute path to the repository root (in this project, always server.js's PROJECT_ROOT = __dirname).
    • File on disk: .env at that root (template: .env.example).
    • node_modules/dotenv — optional; declared in package.json.
  • 📤 Outputs: Populated process.env (PORT, FILES_ROOT, plus any other keys present in .env); at most one console.warn line; no exceptions, ever.
  • 🔗 Project Dependencies:
    • Depends on: fs, path (module scope), dotenv (optional), parseEnvText (fallback), the .env file.
    • Consumed by: exactly one caller — server.js: loadEnv(PROJECT_ROOT) at module top level, immediately after computing PROJECT_ROOT and immediately before require("./lib/files-service").
    • See also
      server.js — the only consumer, and the owner of the call order.
    • See also
      lib/files-service.js — lazy consumer of the written FILES_ROOT.
    • See also
      package.json — declares "dotenv": "^16.4.7" and the "start": "node server.js" script that triggers this whole chain.
    • See also
      nginx.conf — its /api/ comment states "FILES_ROOT is configured in the Node process .env — not in this file", i.e. this module is the single source of truth for that setting.
  • ⚠️ Breaking Change Warning:
    • Call order is a contract. server.js requires lib/files-service.js after calling loadEnv. That is safe today because files-service reads FILES_ROOT lazily — but if it ever hoists process.env.FILES_ROOT to module top level, any reordering breaks every request with FILES_ROOT_MISSING. Do not "optimise" the boot sequence without reading dox/main/server.dox's Environment Bootstrap section, which documents the same contract from the caller's side.
    • Never-throw is a contract. server.js calls loadEnv with no surrounding try. Letting any error escape here turns a bad .env into a full boot crash instead of a degraded start.
    • Changing path.join(projectRoot, ".env") (filename, or the meaning of projectRoot) means the file silently stops being found — no error, just default port 3000 and eventual FILES_ROOT_MISSING responses.
    • Making dotenv a hard top-level require removes the resilience the header comment promises and breaks boots where node_modules is incomplete.

function loadEnv(projectRoot) {
const envPath = path.join(projectRoot, ".env");
try {
require("dotenv").config({ path: envPath });
return;
} catch {
/* dotenv not installed — parse .env manually */
}
try {
if (fs.existsSync(envPath)) {
parseEnvText(fs.readFileSync(envPath, "utf8"));
}
} catch (err) {
console.warn("Could not read .env:", err.message);
}
}
