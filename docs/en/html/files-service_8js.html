Detailed Description

The filesystem domain layer of the CloudAvid File Portal: resolves FILES_ROOT, sanitises every client-supplied path, walks the download tree, and turns the real disk into the data behind all of server.js's JSON and download APIs.

─────────────────────────────────────────────────────────────────────────────

📖 Overview

🧒 ELI5 Summary

Imagine the portal is a library, and server.js is the librarian at the front desk. Where do the books actually live? In the basement. This file is the basement keeper: the only person with the key to the storage room.

The librarian never walks into the basement. When a visitor asks "what shelves do you have?" the librarian shouts downstairs, and the basement keeper walks the aisles, counts the books, checks the newest arrival dates, and sends a neat list back up. When a visitor asks "hand me that exact box", the basement keeper first checks the request slip very carefully — nobody is allowed to ask for the box marked .. ("two rooms back"), and nobody may leave the storage room. If anything is wrong — the basement is locked (FILES_ROOT missing), it is empty, or the slip is invalid — the keeper sends back a stamped slip of paper saying exactly why (403 PATH_TRAVERSAL, 503 FILES_ROOT_EMPTY, …), which the librarian forwards to the visitor.

Core Responsibilities

  • Sole Owner of FILES_ROOT: Reads process.env.FILES_ROOT (populated from .env by lib/load-env.js), resolves it against the project root, and validates that it exists, is a directory, and is non-empty with at least one visible category folder. No other file in the repository resolves or stats FILES_ROOT except via this module.
  • Path Safety Wall: Converts any client-supplied relative path into a validated absolute path that is provably inside FILES_ROOT, rejecting . / .. segments and NUL bytes, and re-checking with path.relative() after resolution (defence in depth).
  • Directory Listing Engine: listCategories() (with per-category recursive summaries) and listPath() (flat listings at any depth) — the data behind /api/categories and /api/files.
  • Download Resolver: getDownloadTarget() stats a file and returns the { absPath, fileName, size, mtime } bundle that server.js streams with fs.createReadStream. This module never streams; it only decides what may be streamed.
  • Search Engine: searchEntries() — an iterative, depth-capped DFS over the tree with substring name matching, hard entry/limit caps and a truncated flag — the data behind /api/search.
  • Release Feed: listLatestReleases() — a full-tree walk that ranks every visible file by modification time — the data behind /api/releases.
  • Synchronous Health Probe: peekRootSync() — a never-throwing, synchronous snapshot of FILES_ROOT health for /api/health and the startup banner.
  • Structured Failure Contract: serviceError() stamps every failure with an httpStatus and a stable machine-readable code, which server.js's sendServiceError() forwards verbatim as JSON.
  • Hidden-Entry Filter: isHidden() enforces the portal-wide rule that index.html, index.php and dotfiles never appear in any listing anywhere in the product.

🧭 Role in the Overall Architecture

This file is the bottom of the back-end and the only file that touches the downloads tree. The deliberate two-layer split of this project is:

  • server.js = transport layer (HTTP parsing, headers, CORS, streaming, routing, logging). Knows nothing about how paths are validated.
  • lib/files-service.js = domain layer (this file). Knows nothing about HTTP; it never writes headers and never sees a request object. Its only HTTP awareness is the httpStatus numbers it stamps onto errors, a pragmatic exception that lets server.js's generic catch render the right status without a mapping table.

Upward, it is consumed exclusively by server.js, which wires each exported function to exactly one API route. Downward, it depends only on Node built-ins (fs/promises, fs, path) and on the environment contract established by lib/load-env.js. The frontend never calls this module; it consumes its output indirectly through assets/js/services/resource-service.js.

Note
What This File Does NOT Do:
  • It does not serve HTTP. No routing, no headers, no streaming — all of that is server.js (streamDownload, sendJSON).
  • It does not cache. Every call re-reads the disk; all caching in this product lives in the browser (resource-service.js's sessionStorage).
  • It does not enforce the browser-side isHidden() copy — that is a duplicated display-level filter in assets/js/browse.js and assets/js/services/resource-service.js. This module's filter is the authoritative one; the frontend ones are cosmetic backups.
  • It does not read or write file contents. It only stats, lists and resolves paths; even getDownloadTarget() returns metadata, and the bytes are streamed by server.js.

🧩 Block: Core Module Requires (fs/promises, fs, path)

🎯 Purpose
Load the three Node built-ins this module is built from: the promise API for all async directory work, the callback/sync API for the one synchronous probe, and the path toolkit for every safety check.
🧒 ELI5
The basement keeper's three tools: a walkie-talkie that texts back later (fs/promises — "I'll tell you when the shelf count is done"), an instant-answer phone (fs — "right now: does the room exist, yes or no"), and a map of the building (path) so every route between rooms is drawn the same way on every operating system.
⚙️ How It Works (Step-by-Step)
  1. fs/promises is required and bound to the name fs: every listing, stat and walk in this file is async and uses the promise API, which keeps the hot paths (concurrent Promise.all listings) composable.

  3. path is required once and powers every join, resolve, relative and separator handling decision — critical because FILES_ROOT may be a Windows path (D:\CloudAvid\Downloads per .env.example) while all API-facing paths are POSIX-style.
📥 Inputs
  • None (module loading only).
📤 Outputs
  • Three module-local bindings used by every other block in this file.
🔗 Project Dependencies
  • Depends on: Node.js runtime only — no npm dependency, which is why the domain layer keeps working even if node_modules is wiped.
  • Consumed by: nothing at require time; the bindings are used by all functions documented below.
  • Sideways: mirrors server.js's "built-ins first" require style and lib/load-env.js's identical approach.

🧩 Block: Operational Limit Constants

🎯 Purpose
Centralise the guard-rail numbers that keep runaway directories, huge trees and over-broad searches from consuming unbounded time or memory.
🧒 ELI5
Speed limits posted at the basement door: "you may check at most 8000 boxes on one trip, you may descend at most 12 floors, you may put 200 search results on the trolley, and 12 items on the new-arrivals shelf." Posted once so every worker follows the same rules.
⚙️ How It Works (Step-by-Step)
  1. MAX_WALK_ENTRIES = 8000 caps how many visible entries the search and release walks may visit; both loops stop mid-walk when reached.
  2. MAX_WALK_DEPTH = 12 caps recursion/stack depth in summarizeTree, searchEntries and listLatestReleases; deeper directories are silently skipped rather than erroring.
  3. SEARCH_LIMIT = 200 is the default and the hard maximum result count for searchEntries; a client-passed limit is clamped with Math.min so it can never raise the ceiling.
  4. RELEASES_LIMIT = 12 is the default cap for listLatestReleases (hard maximum 50, enforced separately inside that function).
📥 Inputs
  • None (compile-time constants).
📤 Outputs
  • Bounds consumed by summarizeTree, searchEntries, listLatestReleases.
🔗 Project Dependencies
  • Depends on: nothing.
  • Consumed by: the three walking functions below; indirectly by the frontend (resource-service.js caps its own suggestion request at limit: 6, always under the ceiling).
See also
assets/js/services/resource-service.js
⚠️ Breaking Change Warning
These numbers are part of the observable behaviour of three API routes. Raising MAX_WALK_ENTRIES changes the worst-case latency of /api/search and /api/releases (a huge tree = slow responses on the request thread); lowering SEARCH_LIMIT below the frontend's request limits (e.g. limit=6 suggestions) silently truncates autocomplete. MAX_WALK_DEPTH interacts with the repository layout: deeper than 12 nested category folders will vanish from search and releases, which looks like a data bug, not a config change.
💻 Live Source Code:
const MAX_WALK_ENTRIES = 8000;
const MAX_WALK_DEPTH = 12;
const SEARCH_LIMIT = 200;
const RELEASES_LIMIT = 12;

🧩 Function: isHidden(name)

🎯 Purpose
Define, in exactly one place, which filenames are invisible to the whole portal: index pages (which would leak as "files" next to real downloads) and every dotfile.
🧒 ELI5
The keeper's ignore-list taped inside the storage room door: anything called "index" and anything starting with a dot is scenery, not merchandise — even if a visitor asks for it by name, it is not on any shelf list.
⚙️ How It Works (Step-by-Step)
  1. Coerce the argument with String(name || "") so undefined or empty names are treated as hidden rather than crashing a walk.
  2. Lower-case once (l) so INDEX.HTML on a case-insensitive Windows volume is filtered identically to index.html.
  3. Hide when: the name is falsy, or is index.html, or is index.php, or starts with . (catches .git, .env, .htaccess, and macOS .DS_Store).
  4. Note the asymmetric test style: index.html/index.php compare the lower-cased string, while the dotfile check uses the original name — dotfiles are conventionally lower-case, and startsWith(".") is case-agnostic anyway.
📥 Inputs
  • name: a raw directory-entry name (string or falsy).
📤 Outputs
  • boolean — true means "skip this entry in every listing, walk and search result".
🔗 Project Dependencies
  • Depends on: nothing.
  • Consumed by: readVisibleEntries, summarizeTree's walk, searchEntries, listLatestReleases's walk — i.e. every disk-reading path in this file.
  • Sideways: this is the authoritative copy of the rule. The frontend re-implements it defensively in resource-service.js (isHidden used by listFiles) and in browse.js (filtering API rows again at render time).
See also
assets/js/services/resource-service.js
assets/js/browse.js
⚠️ Breaking Change Warning
Adding a name here hides it from every surface at once — categories, listings, search, releases and download listings (though not downloads themselves, which go through getDownloadTarget and do not consult this function). Removing, say, the index.html rule makes web-server index files appear as downloadable products. Note the frontend has its own copies: changing only this function leaves browse.js still filtering the old list, so surfaces can disagree after a partial edit.
💻 Live Source Code:
function isHidden(name) {
const l = String(name || "").toLowerCase();
return !name || l === "index.html" || l === "index.php" || name.startsWith(".");
}

🧩 Function: serviceError(httpStatus, code, message)

🎯 Purpose
The module's single error factory: every failure this file raises is an Error enriched with an HTTP status and a stable machine-readable code, forming the API's error contract.
🧒 ELI5
Pre-printed rejection slips. Instead of the keeper shouting "something went wrong!", every refusal gets a stamp: the desk knows how serious it is (the number) and a short code the visitor's software can recognise (like PATH_TRAVERSAL).
⚙️ How It Works (Step-by-Step)
  1. Construct a plain new Error(message) — the message becomes the human-readable error field of the JSON response.
  2. Attach err.httpStatus — the status server.js's catch block uses as err.httpStatus || 500.
  3. Attach err.code — a SCREAMING_SNAKE identifier that server.js forwards verbatim as the code field, letting the frontend (and humans reading API docs) branch on exact failure kinds.
  4. No stack manipulation, no custom class — deliberately lightweight so ordinary instanceof Error checks and log formatting keep working.
📥 Inputs
  • httpStatus: number (400/403/404/503 in this file).
  • code: stable identifier — INVALID_PATH, PATH_TRAVERSAL, NOT_FOUND, NOT_A_DIRECTORY, NOT_A_FILE, FILES_ROOT_MISSING, FILES_ROOT_NOT_FOUND, FILES_ROOT_NOT_DIRECTORY, FILES_ROOT_EMPTY, FILES_ROOT_NO_CATEGORIES.
  • message: end-user-presentable sentence (surfaced verbatim in JSON).
📤 Outputs
  • An Error with httpStatus and code properties, meant to be thrown.
🔗 Project Dependencies
  • Depends on: nothing.
  • Consumed by: literally every throwing block in this file; and indirectly by server.js's sendServiceError(res, err), which reads exactly these two properties.
See also
server.js
⚠️ Breaking Change Warning
The code strings are a public API contract: resource-service.js's parseError() surfaces them to users and tests/monitors may match on them. Renaming a code (or changing an httpStatus) alters API responses with no compile-time signal. If a new failure path throws a plain Error instead of using this factory, server.js renders it as 500 INTERNAL — an accurate status but a debugging dead-end.
💻 Live Source Code:
function serviceError(httpStatus, code, message) {
const err = new Error(message);
err.httpStatus = httpStatus;
err.code = code;
return err;
}

🧩 Function: resolveConfiguredRoot(projectRoot)

🎯 Purpose
Turn the raw FILES_ROOT environment string into an absolute directory path, failing fast with a dedicated error when the setting is absent.
🧒 ELI5
Reading the label on the basement door. No label? Refuse to guess — go back and tell the manager "the door has no name on it" (503 FILES_ROOT_MISSING). Label can be a full address or directions from the lobby; the keeper knows both dialects.
⚙️ How It Works (Step-by-Step)
  1. Read process.env.FILES_ROOT — populated at boot by lib/load-env.js before server.js requires this module (both are required after loadEnv() runs, so ordering is safe).
  2. Treat undefined, null and whitespace-only values ("" after String(raw).trim()) as "not configured" → throw 503 FILES_ROOT_MISSING. 503 (not 500) is deliberate: it tells the operator this is a configuration problem, and it reads correctly on /api/health-style probes.
  3. Trim once into configured; whitespace around the value in .env is therefore harmless.
  4. If the string is already absolute (path.isAbsolute — true for /srv/cloudavid/downloads on Linux and D:\CloudAvid\Downloads on Windows), resolve it with path.resolve(configured) to normalise separators and collapses.
  5. Otherwise anchor it to the supplied projectRoot (__dirname of server.js) with path.resolve(projectRoot, configured) — this is why .env.example's relative default ./sample-downloads works from any working directory.
📥 Inputs
  • projectRoot: absolute base directory (always PROJECT_ROOT from server.js).
  • Environment: FILES_ROOT (documented in .env.example).
📤 Outputs
  • Absolute, normalised root path string.
  • Throws 503 FILES_ROOT_MISSING when unset/blank.
🔗 Project Dependencies
  • Depends on: process.env.FILES_ROOT (written by lib/load-env.js), Node path, serviceError.
  • Consumed by: getRoot (async path) and peekRootSync (sync path) — the only two call sites.
See also
lib/load-env.js
.env.example
server.js
⚠️ Breaking Change Warning
This is the seam between deployment configuration and the whole product. Renaming the FILES_ROOT key breaks every deployment's .env at once; removing the trim makes "D:\Downloads " (trailing space) resolve to a different directory on Windows; changing the relative-path anchor from projectRoot to process.cwd() breaks npm start from any other working directory and any service manager that starts the app from elsewhere. Security note: it intentionally does not validate what the path is — pointing FILES_ROOT at the source tree would expose the application itself, which is exactly what .env.example's comment warns against.
💻 Live Source Code:
function resolveConfiguredRoot(projectRoot) {
const raw = process.env.FILES_ROOT;
if (raw == null || String(raw).trim() === "") {
throw serviceError(
503,
"FILES_ROOT_MISSING",
"FILES_ROOT is not set. Add it to your .env file."
);
}
const configured = String(raw).trim();
return path.isAbsolute(configured)
? path.resolve(configured)
: path.resolve(projectRoot, configured);
}

🧩 Function: getRoot(projectRoot)

🎯 Purpose
Validate that the configured root actually exists and is a directory, returning the validated absolute root used by every async operation.
🧒 ELI5
Before handing over any list, the keeper walks to the labelled door and actually opens it: locked/missing → "the room isn't there" (503 FILES_ROOT_NOT_FOUND); behind it is a closet, not a room → "that's not a room" (503 FILES_ROOT_NOT_DIRECTORY). Only then does work begin.
⚙️ How It Works (Step-by-Step)
  1. Call resolveConfiguredRoot(projectRoot) (fail-fast on missing env).
  2. await fs.stat(root) on the promise API. Any rejection — ENOENT, permission errors, a file where the path should be, even a dangling junction — is collapsed into one user-facing error 503 FILES_ROOT_NOT_FOUND (the raw catch {} deliberately discards the original cause; the operator is pointed at the .env path, which is the fix in essentially all cases).
  3. Check stat.isDirectory(); a regular file or symlink-to-file at FILES_ROOT throws 503 FILES_ROOT_NOT_DIRECTORY.
  4. Return the validated root string. Note there is no memoisation: every API call re-stats, so an operator can fix FILES_ROOT without restarting the server, at the cost of one stat per request.
📥 Inputs
  • projectRoot (from server.js), process.env.FILES_ROOT.
  • Disk: the configured root directory (existence + type only).
📤 Outputs
  • Promise of the validated absolute root path.
  • Throws 503 FILES_ROOT_MISSING / FILES_ROOT_NOT_FOUND / FILES_ROOT_NOT_DIRECTORY.
🔗 Project Dependencies
  • Depends on: resolveConfiguredRoot, fs/promises, serviceError.
  • Consumed by: the first gate of listCategories, listPath, getDownloadTarget, searchEntries, listLatestReleases.
See also
server.js — the /api/health route and the startup banner use the sync twin peekRootSync instead, because those call sites cannot await, and the sync variant intentionally never throws.
⚠️ Breaking Change Warning
The distinction between the three 503 codes is operator-facing gold: collapse them into one "bad root" error and misconfigured deployments become guesswork. Adding a memoised root cache would remove the "fix `.env` and just retry" behaviour. Swapping fs.stat for fsSync.statSync here would make a missing root crash the request path synchronously inside async handlers — the async/throw boundary must stay intact for server.js's catch to convert these into JSON errors rather than unhandled rejections.
💻 Live Source Code:
async function getRoot(projectRoot) {
const root = resolveConfiguredRoot(projectRoot);
let stat;
try {
stat = await fs.stat(root);
} catch {
throw serviceError(
503,
"FILES_ROOT_NOT_FOUND",
"FILES_ROOT does not exist. Check the path in your .env file."
);
}
if (!stat.isDirectory()) {
throw serviceError(
503,
"FILES_ROOT_NOT_DIRECTORY",
"FILES_ROOT exists but is not a directory."
);
}
return root;
}

🧩 Function: splitRel(relPath)

🎯 Purpose
Normalise any client-supplied relative path into a clean array of segments — the input normaliser for the path-safety wall.
🧒 ELI5
Reading the visitor's scribbled directions and rewriting them as a clean list of room names: cross out blanks, fix back-slashes, drop the empty bits, and only then start walking.
⚙️ How It Works (Step-by-Step)
  1. String(relPath || "") — undefined/null become an empty path (which callers interpret as "the root itself").
  2. replace(/\\/g, "/") — accept Windows-style separators from clients (URLs or query strings may carry backslashes) and unify to POSIX.
  3. split("/") then .map(p => p.trim()) — tolerate accidental spaces around segments ("my folder" survives as two clean segments).
  4. .filter(Boolean) — drop empty segments, so trailing slashes (/api/files/docs/) and double slashes (docs//sub) never reach path.resolve as meaningful parts.
📥 Inputs
  • relPath: raw client path (string, possibly undefined, either separator style, possibly with empty segments).
📤 Outputs
  • Array of non-empty, trimmed segment strings ([] for the root).
🔗 Project Dependencies
  • Depends on: nothing.
  • Consumed by: resolveInsideRoot exclusively.
See also
assets/js/services/resource-service.js — the frontend's encodeRelPath() is the mirror-image producer: it also backslash-normalises, filters empties, then percent-encodes each segment before calling the API, so both ends agree on segment boundaries.
⚠️ Breaking Change Warning
This function defines what a "path segment" means across the whole API surface. If the trim or filter steps disappear, /api/files/docs// starts producing a "" segment which path.resolve treats as harmless — but resolveInsideRoot's relPosix gains double slashes and the returned path values stop round-tripping through the frontend's browseHref/downloadHref builders. Removing the backslash swap makes any Windows-flavoured client path resolve to a single segment named docs\sub — a 404 that looks like missing data.
💻 Live Source Code:
function splitRel(relPath) {
return String(relPath || "")
.replace(/\\/g, "/")
.split("/")
.map((p) => p.trim())
.filter(Boolean);
}

🧩 Function: resolveInsideRoot(root, relPath)

🎯 Purpose
The path-safety wall: convert a validated segment list into an absolute target path that is provably inside FILES_ROOT, or refuse loudly.
🧒 ELI5
The door guard who checks the request slip twice. First he reads each room name for forbidden scribbles (. — this room, .. — the room behind us, invisible zero-characters). Then, after walking the route, he checks the map again: "am I still inside the storage room?" If the visitor cleverly wrote a path that ends up outside, he tears up the slip: 403 PATH_TRAVERSAL.
⚙️ How It Works (Step-by-Step)
  1. splitRel(relPath) normalises the input (above).
  2. Reject explicitly: any segment equal to . or .., or containing a NUL byte (\0) → 400 INVALID_PATH. This is the readable, intention-revealing rejection — a client probing with .. gets a precise 400 rather than a vague 403.
  3. path.resolve(root, ...parts) computes the absolute target. Because hostile segments were removed, this is expected to stay inside — but it is not trusted.
  4. Defence in depth: path.relative(root, target) computes the walk from the root back to the target. If the result starts with .. (the target is outside or a sibling of the root) or is absolute (different drive letter on Windows), the target escaped → throw 403 PATH_TRAVERSAL. This catches anything step 2 could not anticipate — e.g. future Windows device-path quirks, or a root itself containing symlinked directories (note: path.resolve is purely lexical; symlink content is not followed here, only real fs.stat results by callers).
  5. Return { target, parts, relPosix } — the absolute path for disk calls, the clean segments (so callers know depth and final name), and a canonical POSIX relative path for building API-facing path values.
📥 Inputs
  • root: validated absolute root (from getRoot).
  • relPath: raw client path from the URL or ?path= query.
📤 Outputs
  • { target, parts, relPosix } on success.
  • Throws 400 INVALID_PATH or 403 PATH_TRAVERSAL.
🔗 Project Dependencies
  • Depends on: splitRel, path, serviceError.
  • Consumed by: listPath and getDownloadTarget — every route where a client picks the path. Category-only endpoints (listCategories, searchEntries, listLatestReleases) never accept a client path and therefore never pass through here.
  • Sideways: server.js contains a second, independent traversal guard (isInsideRoot, used by serveStatic) for the static-asset tree — two walls for two trees, neither relying on the other.
See also
server.js
⚠️ Breaking Change Warning
This is the module's most security-critical block. Weakening any step — e.g. allowing .. because "the frontend never sends it", or skipping the path.relative re-check — converts /api/download into an arbitrary file read of the server (C:\..., /etc/passwd, the .env itself). Replacing path.relative with target.startsWith(root) reintroduces a classic bypass (the sibling directory /data/downloads-evil starts with /data/downloads). Even renaming the PATH_TRAVERSAL code is a public API change. Treat every edit here as a security review, not a refactor.
💻 Live Source Code:
function resolveInsideRoot(root, relPath) {
const parts = splitRel(relPath);
if (parts.some((p) => p === "." || p === ".." || p.includes("\0"))) {
throw serviceError(400, "INVALID_PATH", "Invalid path.");
}
const target = path.resolve(root, ...parts);
const rel = path.relative(root, target);
if (rel.startsWith("..") || path.isAbsolute(rel)) {
throw serviceError(403, "PATH_TRAVERSAL", "Requested path is outside FILES_ROOT.");
}
return {
target,
parts,
relPosix: parts.join("/"),
};
}

🧩 Function: toPosixRel(root, absPath)

🎯 Purpose
Convert an absolute path that is already known to be inside the root back into the canonical POSIX relative path the API uses as the path field of every listed entry.
🧒 ELI5
Walking back from a real room to the storage-room door and writing down the turns you took — but in the same "aisle/shelf/box" shorthand every customer list is written in, no matter which operating system's dialect the floor plan uses.
⚙️ How It Works (Step-by-Step)
  1. path.relative(root, absPath) — the OS-native relative walk (on Windows this may contain backslashes).
  2. .split(path.sep) — split on the platform separator, not a literal slash, so Windows paths split correctly.
  3. .filter(Boolean) — drop the empty segment produced when absPath is the root (so the root maps to [], and relPosix is "").
  4. .join("/") — re-join with POSIX slashes: the canonical on-the-wire form that resource-service.js later re-encodes segment-by-segment for URLs.
📥 Inputs
  • root: validated root; absPath: an entry's absolute path produced by path.join(target, ent.name).
📤 Outputs
  • POSIX relative path string (e.g. docs/manuals/install-guide.pdf).
🔗 Project Dependencies
  • Depends on: path.
  • Consumed by: listPath (building each entry's path field).
  • Sideways: complements splitRel/resolveInsideRoot — together they guarantee the path values this module emits are exactly the values it accepts back on the next request (a round-trip contract the frontend depends on for browseHref/downloadHref).
See also
assets/js/services/resource-service.js
⚠️ Breaking Change Warning
The output format is a cross-file contract: browse.js feeds these path strings back into /api/files/... and /api/download/..., and home.js builds download links from release paths. If backslashes ever leak into the output (e.g. replacing split(path.sep) with split("/")), Windows deployments break in a confusing way: listings render, but the encoded URL contains \\endiskip and the next request 404s — or worse, falls into resolveInsideRoot's backslash tolerance and traverses somewhere unintended.
💻 Live Source Code:
function toPosixRel(root, absPath) {
return path.relative(root, absPath).split(path.sep).filter(Boolean).join("/");
}

🧩 Function: assertCategoryStructure(root)

🎯 Purpose

🧩 Function: summarizeTree(dir)

🎯 Purpose
Compute a category card's statistics — total visible files, total subfolders, and the most recent modification anywhere beneath the category — the numbers displayed on the home page cards.
🧒 ELI5
Counting one shelf properly: walk every aisle under it, tally boxes and items, and jot down the newest "last touched" date you see. You skip drawers that won't open (unreadable folders) and never go deeper than twelve floors — you'd rather report an approximate count than never come back.
⚙️ How It Works (Step-by-Step)
  1. Zero-initialise fileCount, folderCount, latestModified.
  2. Define the recursive walk(current, depth); the very first guard is if (depth > MAX_WALK_DEPTH) return; — deep trees are silently truncated (documented behaviour, not an error).
  3. fs.readdir(current, { withFileTypes: true }) inside try/catch: an unreadable subdirectory simply ends that branch (skip, don't fail the whole summary).
  4. Per entry: isHidden skips it; directories increment folderCount and recurse; files increment fileCount and get an extra fs.stat(full) to read mtimeMs, keeping the running maximum. (Directories contribute only their children's mtimes — a folder's own rename does not count as content freshness.)
  5. The per-file stat failure is swallowed (/* skip unreadable *\/) — a file vanishing mid-walk must not lose the whole category card.
  6. Return { fileCount, folderCount, latestModified }, with latestModified normalised to null when nothing was stat-able (so callers can fall back).
📥 Inputs
  • dir: absolute category directory path.
  • Disk: the entire subtree, depth-capped.
📤 Outputs
  • Promise of { fileCount, folderCount, latestModified } (latestModified = epoch ms or null).
🔗 Project Dependencies
  • Depends on: fs/promises, path, isHidden, MAX_WALK_DEPTH.
  • Consumed by: listCategories (one call per category, run concurrently via the surrounding Promise.all).
  • Sideways: the output feeds mapCategory in resource-service.js, whose stats.total (files + folders) and stats.latestModified (epoch ms) come straight from here and are rendered by home.js cards.
See also
assets/js/services/resource-service.js
assets/js/home.js
⚠️ Breaking Change Warning
The returned shape is a cross-layer contract (three field names are mapped by the frontend). Raising MAX_WALK_DEPTH here without touching the search/releases walkers makes the home-page counts disagree with search results on deep trees — an inconsistency users will report. Making this stricter (throwing on unreadable branches) turns one bad subfolder into a 503 for the whole home page. Its cost profile also matters: one stat per file, no cache — a category with 50,000 files means 50,000 stats per /api/categories call.
💻 Live Source Code:
async function summarizeTree(dir) {
let fileCount = 0;
let folderCount = 0;
let latestModified = 0;
async function walk(current, depth) {
if (depth > MAX_WALK_DEPTH) return;
let entries;
try {
entries = await fs.readdir(current, { withFileTypes: true });
} catch {
return;
}
for (const ent of entries) {
if (isHidden(ent.name)) continue;
const full = path.join(current, ent.name);
if (ent.isDirectory()) {
folderCount += 1;
await walk(full, depth + 1);
} else if (ent.isFile()) {
fileCount += 1;
try {
const st = await fs.stat(full);
if (st.mtimeMs > latestModified) latestModified = st.mtimeMs;
} catch {
/* skip unreadable */
}
}
}
}
await walk(dir, 0);
return {
fileCount,
folderCount,
latestModified: latestModified || null,
};
}

🧩 Function: searchEntries(projectRoot, query, options)

🎯 Purpose
Search the whole tree for entries whose name contains the query — the engine behind /api/search, the search box and the autocomplete dropdown.
🧒 ELI5
A treasure hunt with a walkie-talkie and a hard stop: walk the aisles (deepest-first stack), check every label against the clue, put matches on the trolley — but when the trolley is full (200) or you've touched 8000 boxes, radio "done, might be more!" (truncated: true) and come back.
⚙️ How It Works (Step-by-Step)
  1. Gates: getRoot then assertCategoryStructure — an unconfigured or empty root yields the standard 503s instead of an empty search page.
  2. Normalise the query once: String(query || "").trim().toLowerCase() — trimming means " firefox " finds firefox.zip; the predicate then stays cheap.
  3. Clamp the limit: Math.min(Number(options.limit) || SEARCH_LIMIT, SEARCH_LIMIT) — server.js passes the raw ?limit= string (e.g. autocomplete.js sends 6); non-numeric falls back to 200, and no client can raise the ceiling.
  4. Seed an explicit stack with { dir: root, rel: "", depth: 0 }. The while loop stack.pop() → depth-first, iterative — no recursion, so MAX_WALK_DEPTH is a filter (continue), not a stack-overflow risk, and deep trees cost time, not crashes.
  5. Per popped directory: depth guard, then readdir(..., withFileTypes: true) in try/catch (unreadable dir → continue, skipping only that branch). scanned counts directories actually read (returned for diagnostics).
  6. Per entry, in order: bail out of the for loop when results.length >= limit || visited >= MAX_WALK_ENTRIES (the mid-directory bail keeps the caps hard); skip hidden; visited counts every visible entry examined (the true work unit).
  7. Directories: always pushed for descent, and additionally matched by name — so a category named "ubuntu" is itself a result, enabling "search finds the folder then browse into it".
  8. Files: matched via nameMatches and pushed as results. Results carry { name, path, type } — note no size/mtime: search stays cheap (no per-result stat) at the cost of less info in the dropdown.
  9. Loop terminates when the stack empties, results hits limit, or visited hits MAX_WALK_ENTRIES.
  10. Return { results, scanned, truncated } where truncated is visited >= MAX_WALK_ENTRIES || results.length >= limit — the flag home.js-style UIs (and future UIs) can use to show "more results exist".
📥 Inputs
  • projectRoot, query (raw ?q= value), options.limit (raw ?limit= string or number).
📤 Outputs
  • Promise of { results: Array<{name, path, type}>, scanned: number, truncated: boolean }.
🔗 Project Dependencies
  • Depends on: getRoot, assertCategoryStructure, nameMatches, isHidden, fs/promises, path, the limit constants.
  • Consumed by: server.js route GET /api/search, called by resource-service.js.search(query, { limit }), consumed by autocomplete.js (debounced, limit: 6 suggestions) and home.js (search page).
See also
server.js
assets/js/services/resource-service.js
assets/js/autocomplete.js
⚠️ Breaking Change Warning
Three contract surfaces here. (1) The response shape { results, scanned, truncated } is read by the frontend verbatim — flattening to a bare array breaks autocomplete.js on deploy. (2) DFS ordering is implicit UX: switching to BFS (stack.shift()) changes which 200 files a broad query returns and in what order — results users have learned. (3) The caps are latency insurance: raising MAX_WALK_ENTRIES on a huge tree makes the search event loop busy for seconds (each readdir is awaited but the walk is sequential), which stalls every route on the single-threaded server, not just search. Also note q is currently unused for pruning directory descent — every directory is explored regardless of name match; adding pruning changes which files inside non-matching folders are discoverable.
💻 Live Source Code:
async function searchEntries(projectRoot, query, options = {}) {
const root = await getRoot(projectRoot);
await assertCategoryStructure(root);
const q = String(query || "").trim().toLowerCase();
const limit = Math.min(Number(options.limit) || SEARCH_LIMIT, SEARCH_LIMIT);
const results = [];
let scanned = 0;
let visited = 0;
const stack = [{ dir: root, rel: "", depth: 0 }];
while (stack.length && results.length < limit && visited < MAX_WALK_ENTRIES) {
const { dir, rel, depth } = stack.pop();
if (depth > MAX_WALK_DEPTH) continue;
let entries;
try {
entries = await fs.readdir(dir, { withFileTypes: true });
} catch {
continue;
}
scanned += 1;
for (const ent of entries) {
if (results.length >= limit || visited >= MAX_WALK_ENTRIES) break;
if (isHidden(ent.name)) continue;
visited += 1;
const childRel = rel ? `${rel}/${ent.name}` : ent.name;
const full = path.join(dir, ent.name);
if (ent.isDirectory()) {
stack.push({ dir: full, rel: childRel, depth: depth + 1 });
if (nameMatches(ent.name, q)) {
results.push({
name: ent.name,
path: childRel,
type: "directory",
});
}
} else if (ent.isFile() && nameMatches(ent.name, q)) {
results.push({
name: ent.name,
path: childRel,
type: "file",
});
}
}
}
return { results, scanned, truncated: visited >= MAX_WALK_ENTRIES || results.length >= limit };
}

🎯 Purpose

🧒 ELI5
"Show me the twelve newest things anywhere in the building." The keeper walks every shelf (no shortcut), notes each item's date, sorts the whole pile newest-first, and hands over just the top of the pile.
⚙️ How It Works (Step-by-Step)
  1. Gates: getRoot + assertCategoryStructure (same 503 contract as search).
  2. Clamp the cap: Math.min(Number(limit) || RELEASES_LIMIT, 50) — default 12 (RELEASES_LIMIT), hard maximum 50. server.js passes the raw ?limit= string; resource-service.js's getReleases default is 8.
  3. Recursive async walk(dir, rel, depth): guards on depth > MAX_WALK_DEPTH or visited >= MAX_WALK_ENTRIES (return early — the entry budget is global, not per-branch); readdir in try/catch (unreadable branch → skip); hidden entries skipped; directories recurse with the extended POSIX rel prefix.
  4. Files: fs.stat in try/catch (vanishing file → skip); push { name, path, category, type: "file", size, mtime }. Note the extra category field — childRel.split("/")[0] — which no other function provides; it lets the home page badge each release with its category name without a second lookup.
  5. After the walk: files.sort((a, b) => new Date(b.mtime) - new Date(a.mtime)) — newest first (note b - a: descending). Sorting everything before slicing is what makes this a correct global "latest" rather than "latest per folder".
  6. return files.slice(0, cap).
📥 Inputs
  • projectRoot, limit (raw ?limit= value or default).
📤 Outputs
  • Promise of Array<{ name, path, category, type: "file", size, mtime }> (ISO mtime strings), newest first, length ≤ min(requested, 50).
🔗 Project Dependencies
  • Depends on: getRoot, assertCategoryStructure, isHidden, fs/promises, path, RELEASES_LIMIT, MAX_WALK_DEPTH, MAX_WALK_ENTRIES.
  • Consumed by: server.js route GET /api/releases, fetched by resource-service.js.getReleases(limit) and rendered by home.js as the "latest releases" section (each row's path feeds downloadHref).

The category field is exclusive to this endpoint — dropping it breaks the home page's category labels, not just types. Sorting happens on the full visited set before the cap: a tree with hundreds of thousands of files holds them all in memory briefly per request (this endpoint is the most expensive in the module — no early exit possible, since "latest" is only known after seeing everything). The 50-hard-cap means a client asking limit=1000 silently gets 50 — intentionally, but any frontend change relying on larger feeds must raise the constant here. truncated is not reported by this function (unlike searchEntries); on trees that exceed MAX_WALK_ENTRIES the feed silently covers only the first-visited portion — a subtle correctness boundary worth knowing before touching the walk.

async function listLatestReleases(projectRoot, limit = RELEASES_LIMIT) {
const root = await getRoot(projectRoot);
await assertCategoryStructure(root);
const cap = Math.min(Number(limit) || RELEASES_LIMIT, 50);
const files = [];
let visited = 0;
async function walk(dir, rel, depth) {
if (depth > MAX_WALK_DEPTH || visited >= MAX_WALK_ENTRIES) return;
let entries;
try {
entries = await fs.readdir(dir, { withFileTypes: true });
} catch {
return;
}
for (const ent of entries) {
if (visited >= MAX_WALK_ENTRIES) return;
if (isHidden(ent.name)) continue;
visited += 1;
const childRel = rel ? `${rel}/${ent.name}` : ent.name;
const full = path.join(dir, ent.name);
if (ent.isDirectory()) {
await walk(full, childRel, depth + 1);
} else if (ent.isFile()) {
try {
const st = await fs.stat(full);
files.push({
name: ent.name,
path: childRel,
category: childRel.split("/")[0] || "",
type: "file",
size: st.size,
mtime: st.mtime.toISOString(),
});
} catch {
/* skip */
}
}
}
}
await walk(root, "", 0);
files.sort((a, b) => new Date(b.mtime) - new Date(a.mtime));
return files.slice(0, cap);
}

🧩 Function: peekRootSync(projectRoot)

🎯 Purpose
A synchronous, never-throwing snapshot of FILES_ROOT health for two callers that cannot await: server.js's startup banner and the /api/health (and /__health) endpoint.
🧒 ELI5
A five-second hallway check with a guarantee: "I will come back with an answer, even if the answer is 'I couldn't even check'." It never shouts, never refuses to answer — it just reports three yes/no facts and, if it failed, why as a code.
⚙️ How It Works (Step-by-Step)
  1. Wrap everything in try/catch — this is the module's only never-throw public function (health probes must never 500).
  2. Inside try: resolveConfiguredRoot(projectRoot) (throws FILES_ROOT_MISSING if unset), then fsSync.existsSync(root) — the sync API is deliberate: the startup banner runs inside server.listen's callback, and the health handler wants a one-shot answer without async plumbing in its hot path.
  3. isDir via fsSync.statSync(root).isDirectory(), guarded by exists && so a missing root never triggers a second throw.
  4. Return the happy shape: { configured: true, exists, isDirectory }.
  5. In catch (err): return the diagnostic shape — configured: err.code !== "FILES_ROOT_MISSING" (distinguishing "not configured" from "configured but broken"), exists: false, isDirectory: false, and error: err.code || "UNKNOWN" — the serviceError code, which is precisely why the codes are stable identifiers.
📥 Inputs
  • projectRoot; environment FILES_ROOT; disk stat of the root (sync).
📤 Outputs
  • { configured, exists, isDirectory } or { configured, exists: false, isDirectory: false, error } — plain data, never throws.
🔗 Project Dependencies
  • Depends on: resolveConfiguredRoot, fsSync (callback fs module), and indirectly on serviceError's codes.
  • Consumed by: server.js twice — inside the /api/health handler (the status: "ok" | "degraded", filesRootConfigured, filesRootReady fields are computed directly from this result) and in the server.listen startup banner (the green/yellow FILES_ROOT is… line).
See also
server.js
⚠️ Breaking Change Warning
The result shape is read field-by-field by server.js's health JSON — uptime monitors and dashboards key on status: "ok" which is computed as configured && exists && isDirectory from these three booleans. Changing field names flips production health checks to "degraded" with zero code errors. Removing the catch would violate the never-throw contract: /api/health would fall into sendServiceError and start 500-ing exactly when operators need it most. And using the promise fs here would change the return type to a Promise, silently making every boolean field undefined (truthiness checks in the banner would still "work", producing confidently wrong health reports).

function peekRootSync(projectRoot) {
try {
const root = resolveConfiguredRoot(projectRoot);
const exists = fsSync.existsSync(root);
const isDir = exists && fsSync.statSync(root).isDirectory();
return { configured: true, exists, isDirectory: isDir };
} catch (err) {
return {
configured: err.code !== "FILES_ROOT_MISSING",
exists: false,
isDirectory: false,
error: err.code || "UNKNOWN",
};
}
}
