Detailed Description

The Node.js back-end of the CloudAvid File Portal: a zero-framework HTTP server that serves the SPA shell, static assets, a filesystem-driven JSON API, and streamed downloads.

─────────────────────────────────────────────────────────────────────────────

📖 Overview

🧒 ELI5 Summary

Think of this file as the reception desk of a building.

You (the browser) walk in the front door and say things like: "I want the welcome brochure" (the index.html page), or "Can I see the list of rooms?" (/api/categories), or "Please hand me the big box in room 3, shelf 2" (/api/download/...). The receptionist — this file — never builds the rooms itself and never touches the boxes directly. It just listens to what you ask for, checks that you are allowed to have it, and then calls the right specialist (the modules in lib/) who does the actual walking-and-fetching. If you ask for something dangerous — like "give me the staff-only key cabinet" (/lib/, /.env) — the receptionist politely but firmly says "403 Forbidden" and does not even look inside.

Core Responsibilities

  • HTTP Endpoint: Creates the single Node.js http.Server for the whole project and binds it to 0.0.0.0 on the configured port. It is the only network listener in the repository.
  • Environment Bootstrap: Loads process.env from the project-root .env file (via lib/load-env.js) before anything else reads it.
  • JSON API Router: Implements six API endpoints (/api/health, /api/categories, /api/releases, /api/search, /api/files, /api/download) by delegating all filesystem work to lib/files-service.js.
  • SPA Fallback Server: Returns index.html for /, /browse, and any unknown HTML-ish route, so client-side routing (assets/js/router.js) works on refresh and deep links.
  • Static Asset Server: Serves assets/, fonts, icons and other files from the project root with a curated MIME table, a one-hour cache policy, and an inline SVG placeholder for missing images.
  • Security Gatekeeper: Blocks path traversal, blocks access to /.env, /lib/, /node_modules/, sets nosniff / SAMEORIGIN / strict-origin-when-cross-origin headers on every served response, and sanitises the Content-Disposition filename of downloads.
  • Cross-Origin Enabler: Answers CORS preflights (OPTIONS) and stamps Access-Control-Allow-Origin: * on every JSON and download response, because nginx.conf proxies only the /api/ prefix and other origins may call the API directly.
  • Ops Surface: Colour-coded request logging, a startup banner that reports the health of FILES_ROOT, a health endpoint for uptime monitors, and a graceful SIGINT shutdown handler.

🧭 Role in the Overall Architecture

server.js is the front door of the back-end. It contains zero filesystem logic of its own; every read, stat, walk and safety check on the downloads tree is delegated to lib/files-service.js. This is a deliberate two-layer split:

  • server.js = transport layer (HTTP, headers, streaming, CORS, routing).
  • lib/files-service.js = domain layer (FILES_ROOT resolution, path sanitisation, directory walking, search, release ranking).

The frontend mirror of this split is assets/js/services/resource-service.js, which is the only frontend file allowed to call this server's API.

🧩 Block: PROJECT_ROOT and Environment Bootstrap

📍 Location
Right after the requires.
🎯 Purpose (ELI5)
This is the receptionist pinning the building map on the wall. PROJECT_ROOT says "everything I serve lives here", and loadEnv pastes the office rulebook (.env) onto the wall so every later decision — which port, where the downloads live — can read it.
⚙️ How It Works (Senior Depth)
__dirname is the directory containing server.js, i.e. the repository root in this project's layout. loadEnv(PROJECT_ROOT) therefore resolves <project root>/.env. The call happens synchronously at module top level, before files-service is required — this ordering is load-bearing: PORT below and FILES_ROOT (read lazily by lib/files-service.js) both assume process.env is already populated. loadEnv prefers the dotenv package and silently falls back to a hand-rolled parser if it is not installed, and it never overwrites an existing environment variable.
📥 Inputs
  • File on disk: .env (template: .env.example — keys PORT, FILES_ROOT).
📤 Outputs
  • Populated process.env.PORT and process.env.FILES_ROOT for the whole Node process.
  • PROJECT_ROOT constant used by every API handler and passed as the first argument to every lib/files-service.js call.
🔗 Trace Downward
  • Depends on lib/load-env.js → loadEnv(), which depends on the dotenv package (optional) and fs/path.
  • Depends on node_modules/dotenv being installed (it is declared in package.json).
🔗 Trace Upward
  • .env.example documents the two keys this bootstrap makes real; DevOps copy it to .env on deploy.
  • nginx.conf deliberately does not configure FILES_ROOT — its comment says "FILES_ROOT is configured in the Node process .env — not in this file", i.e. this bootstrap is the single source of truth.
  • package.json's "start": "node server.js" is the command that triggers this whole sequence.
🤝 Trace Sideways
The "pass `PROJECT_ROOT` into the service" convention is the reason lib/files-service.js can stay testable and location-agnostic: every exported function there (listCategories, listPath, getDownloadTarget, searchEntries, listLatestReleases, peekRootSync) takes projectRoot as its first parameter instead of importing a global.
💻 Actual Code
const PROJECT_ROOT = __dirname;
const { loadEnv } = require("./lib/load-env");
loadEnv(PROJECT_ROOT);
const filesService = require("./lib/files-service");

⚠️ Breaking Change Warning Reordering these lines — e.g. requiring lib/files-service.js before calling loadEnv — still works today only because files-service reads FILES_ROOT lazily inside each request. But if files-service ever gains top-level process.env.FILES_ROOT capture (a natural "optimisation"), that reordering would make every request 503 with FILES_ROOT_MISSING. Treat the call order here as a contract, not a style choice. Renaming PROJECT_ROOT also breaks nothing internally, but any new file that mirrors this pattern should keep the same name for greppability.

🧩 Block: HOST, PORT and ROOT Constants

📍 Location
Directly after the files-service require.
🎯 Purpose (ELI5)
The desk's address: which door to open (HOST), which number plate to hang on it (PORT), and a nickname for the building (ROOT).
⚙️ How It Works (Senior Depth)
  • HOST = "0.0.0.0" binds to all interfaces. That is what allows nginx.conf to reach this process over the loopback interface (proxy_pass http://127.0.0.1:3000;) without any socket tricks. It also means the port is reachable from the network, so the security blocklist later in the request handler is not merely theoretical.
  • PORT reads process.env.PORT with a 3000 fallback. Note the truthiness form: PORT=0 in .env would fall through to 3000 rather than picking a random OS port — an edge case worth knowing before "fixing" it.
  • ROOT = PROJECT_ROOT is an alias kept purely for readability at the call sites (isInsideRoot(ROOT, fp), path.join(ROOT, ...), path.join(ROOT, "index.html")).
📥 Inputs
  • process.env.PORT (set by the .env bootstrap above; documented in .env.example as "HTTP port for the Node.js server").
📤 Outputs
  • The listen target used by server.listen(PORT, HOST, ...).
  • The http://localhost:${PORT} base used by decodePathname and by the new URL(req.url, ...) parsing in the main handler.
🔗 Trace Upward
nginx.conf hardcodes the expectation of this port in proxy_pass http://127.0.0.1:3000. Changing the default 3000 here without editing nginx.conf (or setting PORT in .env to match) silently 502s the whole production site.
🤝 Trace Sideways
PORT also appears in lib/load-env.js's domain (via .env) and in the printed URLs of the startup banner. The frontend never needs to know it: every fetch in assets/js/services/resource-service.js uses relative URLs ("/api/categories"), which is exactly what makes the nginx proxy transparent.
💻 Actual Code
const HOST = "0.0.0.0";
const PORT = process.env.PORT || 3000;
const ROOT = PROJECT_ROOT;

⚠️ Breaking Change Warning Changing HOST to "127.0.0.1" for "safety" is a behaviour change: in container deployments that port-map the service, health checks and the nginx upstream must both agree with the new bind address. Changing the default port breaks nginx.conf (see above) and the instructions printed in the startup banner.

🧩 Block: The ANSI Colour Palette c

📍 Location
After the host/port constants.
🎯 Purpose (ELI5)
A box of highlighter pens for the terminal. Each pen is a tiny invisible code that makes the next text a colour, and reset is the cap that stops the colour bleeding onto everything after it.
⚙️ How It Works (Senior Depth)
Plain string map of ANSI escape sequences — no chalk, no dependency. The keys are used in exactly three places: log() (status colouring), and the startup banner + SIGINT handler (cyan/yellow/green emphasis). 📥 Inputs
None — a constant.
📤 Outputs
Colour-wrapped fragments interpolated into template literals in log(), server.listen's banner, and the shutdown message.
🤝 Trace Sideways
Dependency-free "small utility" is a house pattern: lib/load-env.js hand-rolls .env parsing for the same reason. The palette has no counterpart on the frontend — browser logs there are uncoloured.

🧩 Block: The MIME Table MIMES

📍 Location
After the colour palette.
🎯 Purpose (ELI5)
This is the sticker machine at the shipping counter. Every file that leaves the building gets a sticker saying what it is — a picture, a web page, a zip — so the receiver's browser knows whether to display it, play it, or offer a download.
⚙️ How It Works (Senior Depth)
An extension → Content-Type map consulted in three places:
  1. serveStatic — picks the header for static assets (MIMES[ext] || "application/octet-stream").
  2. streamDownload — same fallback for downloads, so a .iso arrives as application/octet-stream and a .pdf as application/pdf even though Content-Disposition: attachment forces the save dialog anyway.
  3. The SPA route — the odd one out: if (ext && MIMES[ext] && ext !== ".html") uses the table as an extension whitelist to decide whether a /browse/...-style path is a real asset (serve statically) or a client route (serve the SPA shell). Text entries carry charset=utf-8; binary entries deliberately do not. Note the table doubles as the project's "supported download catalogue": .iso, .qcow2, .vmdk, .docx, .vsdx are here because this portal distributes VM images and Office/Visio documents.
📥 Inputs
None — a constant.
📤 Outputs
Content-Type header values for every static and download response; an extension-membership test for the SPA-vs-static routing decision.
🔗 Trace Upward
The extensions listed here are the ones the frontend will happily link to: assets/js/router.js keeps its own fileExtensions regex (html, zip, tar, gz, iso, qcow2, vmdk, pdf, txt, log, sql, docx, xlsx, pptx, png, jpg, exec, sh, yml, yaml, md, json, csv) to decide which links must not be SPA-navigated but downloaded/navigated natively. The two lists overlap on purpose but are not identical — adding a new extension here (e.g. .deb) makes the server serve it correctly, while adding it to router.js's regex is what stops the SPA from hijacking clicks on such links.
🔗 Trace Downward
serveStatic also uses ext to pick the cache policy (no-cache for .html, public, max-age=3600 for everything else) and to decide whether a missing file should become the inline SVG placeholder (images list) or the SPA fallback (.html / extensionless).
🤝 Trace Sideways
The same "map instead of library" minimalism as the c palette. The frontend mirrors the pattern conceptually with inferIcon() in assets/js/services/resource-service.js, which maps filename patterns to icon categories.

🧩 Function: log(method, status, url, extra)

📍 Location
Between the MIME table and sendJSON.
🎯 Purpose (ELI5)
After every visitor interaction, the receptionist writes one line in the day-book: time, what they asked, and how it went — written in green when everything went fine, yellow when something was their mistake, red when the building itself is on fire.
⚙️ How It Works (Senior Depth)
Picks a colour from the c palette by status band (≥500 red, ≥400 yellow, ≥300 cyan, else green), timestamps with a HH:MM:SS slice of the ISO date, and pads the method to 6 characters with padEnd(6) so columns line up. Called from every terminal branch of the request handler and from the blocklist guard, always after the response has been produced, so a logging bug can never corrupt a response.
📥 Inputs
  • method — e.g. "GET", "HEAD".
  • status — numeric HTTP status.
  • url — the decoded pathname.
  • extra — optional suffix: latency (${Date.now() - start}ms), item counts (${categories.length} categories · …), service error codes.
📤 Outputs
One console.log line per handled request. No file logging — nginx.conf disables access_log for static assets and expects the Node process's stdout to be captured by the platform service manager.
🔗 Trace Upward
Consumed exclusively inside this file by the main request handler, the blocklist branch, and every API/SPA/static branch (always with the Date.now() - start latency suffix).
🤝 Trace Sideways
The frontend has a different observability culture: assets/js/services/ performance-monitor.js measures client-side performance instead. Server latency strings here ("… · 3ms") are the human-readable counterpart of the Cache-Control: no-store headers the API sends — together they say "the data is fresh and fast".
💻 Actual Code
function log(method, status, url, extra = "") {
const color =
status >= 500 ? c.red :
status >= 400 ? c.yellow :
status >= 300 ? c.cyan :
c.green;
const time = new Date().toISOString().slice(11, 19);
console.log(
`${c.dim}${time}${c.reset} ${c.bold}${method.padEnd(6)}${c.reset} ${color}${status}${c.reset} ${url} ${c.dim}${extra}${c.reset}`
);
}

⚠️ Breaking Change Warning Change the signature and every call site in this file must change too. Change the format and anything tailing stdout (log shippers, journalctl filters, alerting regexes on status codes) loses its anchors. Do not route log() through anything that can throw synchronously — it runs inside the request handler's try, so a throwing logger would convert successful responses into the 500 path of sendServiceError.

🧩 Function: sendJSON(res, status, data, headers)

📍 Location
After log.
🎯 Purpose (ELI5)
The standard envelope the receptionist puts answers in: a clean white envelope (JSON), the right stamp (Content-Type), the exact weight (Content-Length), and a sticker saying "anyone may open this" (Access-Control-Allow-Origin: *).
⚙️ How It Works (Senior Depth)
Serialises with JSON.stringify(data, null, 0) (compact), writes a header set with sensible API defaults, then spreads the caller's headers last so a call site can override any default. Every API handler in the main router funnels through this function; sendServiceError uses it too, which is how error payloads inherit the same CORS/caching policy as successes. Content-Length is computed with Buffer.byteLength(body) — correct for multi-byte UTF-8 payloads (e.g. non-ASCII filenames in search results), which body.length would get wrong.
📥 Inputs
  • res — the ServerResponse.
  • status — HTTP status code.
  • data — any JSON-serialisable value (arrays for listings, objects for health/errors).
  • headers — optional per-call overrides (currently unused by call sites, kept for future needs).
📤 Outputs
Default headers written: "Content-Type": "application/json; charset=utf-8", "Content-Length", "Access-Control-Allow-Origin": "*", "Access-Control-Allow-Methods": "GET, HEAD, OPTIONS", "Access-Control-Allow-Headers": "Content-Type", "Cache-Control": "no-store" — then the body.
🔗 Trace Upward
The most important consumer is assets/js/services/resource-service.js: its getCachedData/setCachedData implement their own 5-minute sessionStorage cache precisely because this endpoint sends Cache-Control: no-store (the HTTP cache is told never to help). Its parseError() also depends on this function's shape: res.json() is expected to yield { error: "..." } for non-OK statuses.
🔗 Trace Downward
Depends on nothing outside Node core; it is a dependency of every API branch below and of sendServiceError.
🤝 Trace Sideways
sendText is its text-bodied sibling with a reduced header set; both exist so HEAD/static/error paths never accidentally inherit the JSON content type.
💻 Actual Code
function sendJSON(res, status, data, headers = {}) {
const body = JSON.stringify(data, null, 0);
res.writeHead(status, {
"Content-Type": "application/json; charset=utf-8",
"Content-Length": Buffer.byteLength(body),
"Access-Control-Allow-Origin": "*",
"Access-Control-Allow-Methods": "GET, HEAD, OPTIONS",
"Access-Control-Allow-Headers": "Content-Type",
"Cache-Control": "no-store",
...headers,
});
res.end(body);
}

⚠️ Breaking Change Warning This is the API contract writer. Narrowing Access-Control-Allow-Origin from * to a specific origin breaks any direct (non-nginx-proxied) API consumer. Removing Cache-Control: no-store turns the frontend's sessionStorage + browser-cache combination into a double cache whose invalidation you do not control. Changing the error payload shape ({ error, code }, see sendServiceError) breaks parseError() in resource-service.js and the user-visible error messages of the entire portal.

🧩 Function: sendText(res, status, text, contentType)

📍 Location
After sendJSON.
🎯 Purpose (ELI5)
The sticky-note version of an answer: short, plain text, no envelope. Used when there is nothing structured to say — "Forbidden", "404 — whatever you typed", "Bad Request".
⚙️ How It Works (Senior Depth)
Writes only Content-Type (defaulting to text/plain; charset=utf-8, overridable) and Access-Control-Allow-Origin: *, then the body. Note the deliberate differences from sendJSON: no Content-Length (Node uses chunked encoding), and no Cache-Control (errors are cacheable per HTTP defaults, which is acceptable for these never-changing messages).
📥 Inputs
  • res, status, text, optional contentType.
📤 Outputs
A plain-text response body with CORS enabled.
🔗 Trace Upward
Called from: URL-parse failure (400), method guard (405), the security blocklist (403), serveStatic (403 traversal, 404 missing asset), serveSPA (500 when index.html is missing), streamDownload (500 when the read stream errors before headers are sent). It is this file's universal "say something honest, quickly" path.
🤝 Trace Sideways
Frontend error handling rarely surfaces these raw strings: for API calls, resource-service.js's parseError() prefers the JSON {error} body from sendServiceError; for page navigation, router.js simply lets the browser display the text.
💻 Actual Code
function sendText(res, status, text, contentType = "text/plain; charset=utf-8") {
res.writeHead(status, {
"Content-Type": contentType,
"Access-Control-Allow-Origin": "*",
});
res.end(text);
}

⚠️ Breaking Change Warning Adding Cache-Control headers here would change how browsers and upstream proxies (nginx in production) cache error responses — with a long max-age, a single transient 500 for index.html could stick at the proxy. Removing the CORS header breaks browser-visible error text for cross-origin API consumers. Keep this function boring; it is the last line of defence when everything else has already gone wrong.

🧩 Function: sendServiceError(res, err)

📍 Location
After sendText.
🎯 Purpose (ELI5)
The translator between the specialists in the back office and the visitor. When a specialist hands the receptionist a slip saying "this shelf does not exist" or "you may not go in there", this turns the slip into a proper, polite JSON answer with the right number on it.
⚙️ How It Works (Senior Depth)
Reads two duck-typed properties that lib/files-service.js's serviceError() attaches to plain Error objects: err.httpStatus (default 500) and err.code (default "INTERNAL"). Responds with { error: err.message || "Unexpected error", code: err.code || "INTERNAL" }. The || defaults make the function safe for unexpected errors (a real TypeError, an fs error without annotations) as well as expected service errors — this is the single convergence point of the main handler's catch (err).
📥 Inputs
  • err — any thrown value; service errors from lib/files-service.js carry { httpStatus, code, message }.
📤 Outputs
Via sendJSON: e.g. 503 { "error": "FILES_ROOT does not exist…", "code": "FILES_ROOT_NOT_FOUND" } or 403 { "error": "Requested path is outside FILES_ROOT.", "code": "PATH_TRAVERSAL" }.
🔗 Trace Upward
  • assets/js/services/resource-service.js → parseError(res) reads body.error and throws it as a JS Error message; that message is ultimately displayed to users by home.js and browse.js in their error cards.

🧩 Function: contentDisposition(fileName)

📍 Location
After relFromPrefix.
🎯 Purpose (ELI5)
The shipping label writer. When a big box (file download) leaves the building, this writes the recipient's name on it twice: once in simple letters everyone can read, and once in "international handwriting" so names in any language (yes, even Persian!) survive the trip.

📤 Outputs
A complete header value, e.g. attachment; filename="win11_iso"; filename*=UTF-8''win11.iso.
🔗 Trace Upward
Filenames arrive from FILES_ROOT (arbitrary, user-curated names — that is the whole point of a file portal) after validation by lib/files-service.js. The attachment disposition is the third layer of download safety, alongside X-Content-Type-Options: nosniff (same header block in streamDownload) and the NOT_A_FILE type check in the service.

Pure string manipulation — no dependencies beyond the JS standard library.
🤝 Trace Sideways

🧩 Function: serveStatic(reqPath, res)

📍 Location
After serveSPA.
🎯 Purpose (ELI5)
The supply closet attendant. Every picture, stylesheet, script and font the brochure mentions lives in this closet. You ask by name, the attendant checks you're not asking for something outside the closet (no peeking into the office!), finds the box, sticks the right label on it, and hands it over. If a picture is missing, they hand you a friendly little "picture not found" doodle instead of an error page. ⚙️ How It Works (Senior Depth)
Four phases, in order:
  1. Path sanitisation — path.normalize(reqPath).replace(/^(\.\.[\/\\])+/, "") collapses dot-segments and strips leading parent-jumps; path.join(ROOT, …) maps / and "" to index.html; the extension is lowercased once.
  2. Traversal guard — isInsideRoot(ROOT, fp) plus an explicit re-admission of index.html; violations get 403 Forbidden via sendText.
  3. Contentful fallbacks (inside fs.readFile's error callback): missing images (png/jpg/jpeg/webp/ico/svg) get an inline 64×64 SVG placeholder (a 200 response with image/svg+xml!); missing pages (.html or no extension) get serveSPA(res); anything else gets 404 — ${reqPath}.
  4. Success — securityHeaders(res), then writeHead(200) with the MIME from MIMES (fallback application/octet-stream) and a cache policy: no-cache for .html, public, max-age=3600 (one hour) otherwise.
📥 Inputs
  • reqPath — the decoded pathname (e.g. /assets/css/base.css).
  • Files on disk under the project root: assets/**, fonts, favicon.
📤 Outputs
Static bytes + headers, or one of the three fallbacks above.
🔗 Trace Upward
Called from the main router's final serveStatic(pathname, res) branch and from the SPA branch when the path has a known non-HTML extension. The consumers are the <link>/<img>/<script> tags of index.html (tokens.css, base.css, components.css, home.css, browse.css, performance-modes.css, /assets/icon/logo.webp, /assets/icon/files-logo.webp, all eight deferred scripts) and the runtime-injected markup of home.js/browse.js/autocomplete.js.
🔗 Trace Downward
Depends on path, fs, isInsideRoot, MIMES, securityHeaders, sendText, serveSPA, and the inline SVG string constant embedded below.
🤝 Trace Sideways
The inline-SVG-on-404 trick is why the navbar logo carries an inline onerror="this.style.display='none'" in index.html — the frontend has its own missing-image fallback, and the two coexist (server fallback for <img> loads that never reach JS handlers, onerror for robustness). nginx implements the same "serve assets with long cache" concept via its regex location (30d, immutable) — production caches longer than dev.
💻 Actual Code
function serveStatic(reqPath, res) {
const safe = path.normalize(reqPath).replace(/^(\.\.[\/\\])+/, "");
const fp = path.join(ROOT, safe === "/" || safe === "" ? "index.html" : safe);
const ext = path.extname(fp).toLowerCase();
if (!isInsideRoot(ROOT, fp) && path.resolve(fp) !== path.resolve(ROOT, "index.html")) {
sendText(res, 403, "Forbidden");
return;
}
fs.readFile(fp, (err, data) => {
if (err) {
if ([".png", ".jpg", ".jpeg", ".webp", ".ico", ".svg"].includes(ext)) {
const svg = `<svg xmlns="http://www.w3.org/2000/svg" width="64" height="64" viewBox="0 0 24 24" fill="none" stroke="#64748b" stroke-width="1.5"><rect x="3" y="3" width="18" height="18" rx="3" opacity="0.3"/><circle cx="9" cy="9" r="2"/><path d="m21 15-3.086-3.086a2 2 0 0 0-2.828 0L6 21"/></svg>`;
res.writeHead(200, { "Content-Type": "image/svg+xml" });
res.end(svg);
return;
}
if (!ext || ext === ".html") {
serveSPA(res);
return;
}
sendText(res, 404, `404 — ${reqPath}`);
return;
}
securityHeaders(res);
res.writeHead(200, {
"Content-Type": MIMES[ext] || "application/octet-stream",
"Cache-Control": ext === ".html" ? "no-cache" : "public, max-age=3600",
});
res.end(data);
});
}

Note the SVG fallback deliberately answers 200 — that is what keeps <img> elements rendering; changing it to 404 must be coordinated with the onerror handler on the logo in index.html.

🧩 Function: streamDownload(req, res, fileInfo)

📍 Location
After serveStatic.
🎯 Purpose (ELI5)
The big-box counter. Small answers go in envelopes; a 5-gigabyte disk image goes into a stream — the receptionist starts rolling the box out the door immediately, piece by piece, instead of trying to lift the whole thing at once. And if the customer hangs up halfway, they stop rolling immediately too.
⚙️ How It Works (Senior Depth)
Builds headers from fileInfo (produced by filesService.getDownloadTarget, which has already validated existence and file-ness): MIME from MIMES (fallback octet-stream), exact Content-Length from stat, the RFC 5987 disposition from contentDisposition, Cache-Control: private, max-age=0, must-revalidate, permissive CORS, and X-Content-Type-Options: nosniff. Three lifecycle details make it production-grade:
  1. HEAD support — headers only, res.end() with no body.
  2. Security headers before streaming — securityHeaders(res) then writeHead.
  3. Backpressure & cancellation — fs.createReadStream(...).pipe(res) honours TCP backpressure; stream.on("error") answers 500 only if headers have not been sent yet (!res.headersSent), otherwise it res.destroy()s mid-flight; req.on("close") destroys the stream so an aborted download stops disk reads.
📥 Inputs
  • req — used for method (HEAD) and the close (abort) event.
  • fileInfo — { absPath, fileName, size, mtime } from lib/files-service.js.
📤 Outputs
A streamed file with Content-Disposition: attachment; ..., or a 500 text response on early read failure.
🔗 Trace Upward
Triggered exclusively by the /api/download router branch. Frontend producers of those URLs: ResourceService.downloadHref() used by home.js (quick-links, search results, release cards), browse.js (file rows), and autocomplete.js (itemHref for non-directory suggestions). Because the SPA never fetches this URL with fetch(), the browser's native download manager is the real consumer — which is why router.js's click interceptor explicitly skips file-extension links.
🔗 Trace Downward
Depends on fs.createReadStream, path.extname, MIMES, contentDisposition, securityHeaders, sendText.
🤝 Trace Sideways
The no-store on JSON endpoints vs private, must-revalidate on downloads mirrors the frontend cache split: resource-service.js caches metadata in sessionStorage for 5 minutes but never caches bytes. nginx.conf proxies this endpoint with proxy_buffering off and 3600s read/send timeouts — the numbers match exactly so a slow multi-GB download is never truncated by the proxy.
💻 Actual Code
function streamDownload(req, res, fileInfo) {
const ext = path.extname(fileInfo.fileName).toLowerCase();
const headers = {
"Content-Type": MIMES[ext] || "application/octet-stream",
"Content-Length": fileInfo.size,
"Content-Disposition": contentDisposition(fileInfo.fileName),
"Cache-Control": "private, max-age=0, must-revalidate",
"Access-Control-Allow-Origin": "*",
"X-Content-Type-Options": "nosniff",
};
if (req.method === "HEAD") {
res.writeHead(200, headers);
res.end();
return;
}
securityHeaders(res);
res.writeHead(200, headers);
const stream = fs.createReadStream(fileInfo.absPath);
stream.on("error", () => {
if (!res.headersSent) sendText(res, 500, "Failed to read file");
else res.destroy();
});
req.on("close", () => stream.destroy());
stream.pipe(res);
}

⚠️ Breaking Change Warning The fileInfo shape (absPath, fileName, size) is a contract with lib/files-service.js's getDownloadTarget. Switching pipe(res) to a manual data/end loop without backpressure can balloon memory on large .iso/.qcow2/.vmdk files — the exact artefacts this portal exists to serve. Removing the req.on("close") handler makes aborted downloads keep reading disk. Removing res.headersSent checking throws ERR_HTTP_HEADERS_SENT on mid-stream failures. And per nginx.conf, the 3600s proxy timeouts assume downloads can legitimately run for an hour; adding buffering (res.end(buffer)) or changing cache headers interacts with that configuration.

🧩 Block: The Main Request Handler — http.createServer(async (req, res) => …)

📍 Location
After streamDownload; the largest single block in the file.
🎯 Purpose (ELI5)
This is the receptionist's actual brain — the big checklist they run through for every single visitor, in the same order every time: understand the request → handle special "may I pass?" pings → reject wrong methods → refuse dangerous doors → answer API questions → hand out pages → hand out closet items → and if anything explodes anywhere along the way, apologise politely in JSON.
⚙️ How It Works (Senior Depth) — Sub-blocks in exact order
🧩 1. Latency timer and URL parsing
Records const start = Date.now() for every log line, then parses req.url into a URL (against the synthetic http://localhost:${PORT} base) and percent-decodes url.pathname into pathname. Any parse or decode failure (URIError from malformed % sequences) lands in the catch with sendText(res, 400, "Bad Request").
🧩 2. CORS preflight (OPTIONS)
Any OPTIONS request gets 204 with Access-Control-Allow-Origin: *, Access-Control-Allow-Methods: GET, HEAD, OPTIONS, Access-Control-Allow-Headers: Content-Type, Access-Control-Max-Age: 86400 (browsers cache the preflight for a day). This is what lets the portal be embedded or driven from other origins even though nginx only proxies /api/.
🧩 3. Method gate
Anything that is not GET or HEAD receives 405 Method Not Allowed before any routing happens — a quiet rejection of POST/PUT/DELETE scanners.
🧩 4. Security blocklist
Three prefixes are refused with 403 Forbidden + a log line: /.env (secrets!), /lib/ (server-side source: files-service.js, load-env.js), /node_modules/ (dependency source). This is the Node-side twin of nginx's location ~ /\. deny rule — both layers must stay because dev traffic skips nginx and production traffic skips neither.
🧩 5. /api/health + /__health
Calls the synchronous filesService.peekRootSync(PROJECT_ROOT) (safe in a hot path: one existsSync/statSync, no awaits) and answers with { status: "ok"|"degraded", service: "CloudAvid File Portal", uptime: process.uptime(), timestamp, filesRootConfigured, filesRootReady }. "ok" requires configured ∧ exists ∧ isDirectory; anything else is "degraded" (HTTP 200 either way, so uptime monitors alert on payload semantics, not status codes).
🧩 6. /api/categories
await filesService.listCategories(PROJECT_ROOT) → array of category objects (name, path, type: "directory", fileCount, folderCount, mtime, latestModified), sorted by name. Logged with the category count and latency.
🧩 7. /api/releases
Reads ?limit= (string or null; the service coerces and caps it), calls listLatestReleases(PROJECT_ROOT, limit) → the newest files across all categories with { name, path, category, type, size, mtime }.
🧩 8. /api/search
Reads ?q= (default "") and ?limit=, calls searchEntries(PROJECT_ROOT, q, { limit }) → { results, scanned, truncated }. Consumers: autocomplete.js (limit 6, debounced) and home.js (full search view).
🧩 9. /api/files and /api/files/...
Dual grammar: bare /api/files takes ?path= from the query string; /api/files/<rel> takes the tail via relFromPrefix. Empty rel lists the category roots. Consumer: ResourceService.listFiles() → browse.js.
🧩 10. /api/download and /api/download/...
Same dual grammar; resolves via getDownloadTarget(PROJECT_ROOT, rel) (which throws typed service errors for traversal/404/not-a-file — caught by the outer catch) and hands the descriptor to streamDownload. This is the only branch that streams bytes instead of JSON.
🧩 11. SPA routes
/, /index.html, /browse, and anything under /browse/ route to the app. A small wrinkle: if the path carries a known non-HTML extension (ext && MIMES[ext] && ext !== ".html"), it is served by serveStatic instead (logged with static), so /browse/logo.svg is an asset while /browse/ISOs/ is a client route. Everything else becomes serveSPA (logged with SPA).
🧩 12. Static fallback
Any other path goes to serveStatic(pathname, res) (logged with asset). Combined with the SPA branch this makes the server's page behaviour identical to nginx's try_files $uri $uri/ @spa.
🧩 13. The error net
The whole routing chain sits in one try: any thrown service error maps through sendServiceError (status from err.httpStatus, payload {error, code}) and is logged with err.code || err.message and latency.
📥 Inputs
  • req.url (path + query), req.method.
  • process.env.FILES_ROOT (read inside the service).
  • The on-disk downloads tree pointed at by FILES_ROOT.
📤 Outputs
JSON for the five read endpoints; streamed bytes for downloads; HTML shell for SPA routes; static bytes for assets; typed errors for everything that fails.

const server = http.createServer(async (req, res) => {
const start = Date.now();
let pathname;
let url;
try {
url = new URL(req.url, `http://localhost:${PORT}`);
pathname = decodeURIComponent(url.pathname);
} catch {
sendText(res, 400, "Bad Request");
return;
}
if (req.method === "OPTIONS") {
res.writeHead(204, {
"Access-Control-Allow-Origin": "*",
"Access-Control-Allow-Methods": "GET, HEAD, OPTIONS",
"Access-Control-Allow-Headers": "Content-Type",
"Access-Control-Max-Age": "86400",
});
res.end();
return;
}
if (req.method !== "GET" && req.method !== "HEAD") {
sendText(res, 405, "Method Not Allowed");
return;
}
const blocked = pathname === "/.env" || pathname.startsWith("/lib/") || pathname.startsWith("/node_modules/");
if (blocked) {
sendText(res, 403, "Forbidden");
log(req.method, 403, pathname);
return;
}
try {
if (pathname === "/__health" || pathname === "/api/health") {
const peek = filesService.peekRootSync(PROJECT_ROOT);
sendJSON(res, 200, {
status: peek.configured && peek.exists && peek.isDirectory ? "ok" : "degraded",
service: "CloudAvid File Portal",
uptime: process.uptime(),
timestamp: new Date().toISOString(),
filesRootConfigured: peek.configured,
filesRootReady: Boolean(peek.exists && peek.isDirectory),
});
log("GET", 200, pathname, `${Date.now() - start}ms`);
return;
}
if (pathname === "/api/categories") {
const categories = await filesService.listCategories(PROJECT_ROOT);
sendJSON(res, 200, categories);
log("GET", 200, pathname, `${categories.length} categories · ${Date.now() - start}ms`);
return;
}
if (pathname === "/api/releases") {
const limit = url.searchParams.get("limit");
const releases = await filesService.listLatestReleases(PROJECT_ROOT, limit);
sendJSON(res, 200, releases);
log("GET", 200, pathname, `${releases.length} · ${Date.now() - start}ms`);
return;
}
if (pathname === "/api/search") {
const q = url.searchParams.get("q") || "";
const limit = url.searchParams.get("limit");
const data = await filesService.searchEntries(PROJECT_ROOT, q, { limit });
sendJSON(res, 200, data);
log("GET", 200, pathname, `${data.results.length} · ${Date.now() - start}ms`);
return;
}
if (pathname === "/api/files" || pathname.startsWith("/api/files/")) {
const rel = pathname === "/api/files"
? (url.searchParams.get("path") || "")
: relFromPrefix(pathname, "/api/files");
const entries = await filesService.listPath(PROJECT_ROOT, rel);
sendJSON(res, 200, entries);
log("GET", 200, pathname, `${entries.length} items · ${Date.now() - start}ms`);
return;
}
if (pathname === "/api/download" || pathname.startsWith("/api/download/")) {
const rel = pathname === "/api/download"
? (url.searchParams.get("path") || "")
: relFromPrefix(pathname, "/api/download");
const fileInfo = await filesService.getDownloadTarget(PROJECT_ROOT, rel);
streamDownload(req, res, fileInfo);
log(req.method, 200, pathname, `${fileInfo.fileName} · ${Date.now() - start}ms`);
return;
}
if (
pathname === "/" ||
pathname === "/index.html" ||
pathname === "/browse" ||
pathname.startsWith("/browse/")
) {
const ext = path.extname(pathname).toLowerCase();
if (ext && MIMES[ext] && ext !== ".html") {
serveStatic(pathname, res);
log("GET", 200, pathname, `static · ${Date.now() - start}ms`);
return;
}
serveSPA(res);
log("GET", 200, pathname, `SPA · ${Date.now() - start}ms`);
return;
}
serveStatic(pathname, res);
log("GET", 200, pathname, `asset · ${Date.now() - start}ms`);
} catch (err) {
const status = err.httpStatus || 500;
sendServiceError(res, err);
log(req.method, status, pathname, `${err.code || err.message} · ${Date.now() - start}ms`);
}
});

🧩 Block: server.listen(PORT, HOST, …) — Startup Banner

📍 Location
Immediately after http.createServer.
🎯 Purpose (ELI5)
The moment the reception desk opens, it pins a big friendly sign on the door: "we are open, here is where the rooms are, and here is whether the archive room actually exists today." That last bit matters — if the manager forgot to write FILES_ROOT on the rulebook, the sign turns yellow and tells you exactly what is missing instead of letting the server limp along mysteriously.
⚙️ How It Works (Senior Depth)
The callback runs once the socket is bound. It calls filesService.peekRootSync(PROJECT_ROOT) and converts the three failure dimensions into a colour-coded status line: not configured → yellow "FILES_ROOT is not set"; missing path → yellow "FILES_ROOT path was not found"; not a directory → yellow "FILES_ROOT is not a directory"; otherwise green "FILES_ROOT is configured". It then prints the boxed banner with all six canonical endpoint URLs. Note the deliberate choice to not exit on a bad FILES_ROOT — the server still starts, health reports "degraded", and API calls will answer typed 503s from lib/files-service.js; this makes misconfiguration observable rather than fatal, which is friendlier to container orchestration that restarts crash-looping processes.
📥 Inputs
  • PORT, HOST constants; FILES_ROOT (via peekRootSync reading process.env).
📤 Outputs
Stdout: the banner, the FILES_ROOT status, the hint "Set FILES_ROOT in .env — no filesystem paths are hardcoded." and "Press Ctrl+C to stop".
🔗 Trace Upward
Triggered by npm start (package.json) in dev, or by the process manager in production behind nginx.conf.
🔗 Trace Downward
Depends on filesService.peekRootSync — the only synchronous export of the service, chosen so the banner never needs async plumbing.
🤝 Trace Sideways
The banner's endpoint list is a human-readable mirror of the router: /api/health, /api/categories, /api/files/<category>, /api/download/<category>/<file>, /api/search?q=, /api/releases. The .env hint mirrors .env.example's comments verbatim in spirit.

🧩 Block: The SIGINT Shutdown Handler

📍 Location
The final statement of server.js.
🎯 Purpose (ELI5)
The closing-time ritual. When the operator presses Ctrl+C, the receptionist doesn't just run out the door mid-sentence — they finish the sentence, politely say "Shutting down file portal…", lock the door, and then turn off the lights.
⚙️ How It Works (Senior Depth)
process.on("SIGINT", …) intercepts Ctrl+C (and the SIGINT signal sent by container stop sequences), prints a yellow notice, and calls server.close(() => process.exit(0)). server.close stops accepting new connections but lets in-flight requests (notably active streamDownload pipes!) finish before the callback fires and exits with code 0. Edge case worth knowing: if a download is streaming and the client never disconnects, close's callback can be delayed indefinitely — that is precisely why streamDownload registers req.on("close") to destroy streams on client disconnects, and why an operator may still need a second Ctrl+C (which, with this handler installed, is captured again and merely re-runs the same path) or a SIGKILL from the orchestrator.
📥 Inputs
  • The OS signal SIGINT.
📤 Outputs
Stdout notice; process exit code 0 after graceful drain.
🔗 Trace Upward
Depended upon by deployment hygiene: nginx.conf's 3600s proxy timeouts imply long-lived download connections, and graceful drain is what makes systemctl restart-style operations not truncate user downloads.
🔗 Trace Downward
Depends on server (the http.Server instance) and console.
🤝 Trace Sideways
The frontend has no equivalent — browsers own their lifecycle. The closest analogue is resource-service.js's clearCache(), another explicit "clean up before leaving" utility.
💻 Actual Code
process.on("SIGINT", () => {
console.log(`\n${c.yellow}Shutting down file portal…${c.reset}`);
server.close(() => process.exit(0));
});

⚠️ Breaking Change Warning Removing this handler reverts Ctrl+C to Node's default: immediate termination, truncated streams, and the nginx.conf upstream briefly serving connection-refused 502s during every restart. Replacing process.exit(0) with a nonzero code can make orchestrators treat planned restarts as crashes. If you later add SIGTERM support (recommended for containers), reuse this same close-and-exit body — two divergent shutdown paths is how zombie downloads happen.
