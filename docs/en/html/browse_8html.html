Detailed Description

Root shell document for the CloudAvid File Portal single-page application (SPA).

─────────────────────────────────────────────────────────────────────────────

📖 Overview

🧒 ELI5 Summary

Imagine you have a really nice picture frame that never changes. The frame has a pretty top piece (the navigation bar with the logo), a pretty bottom piece (the footer with the company name), and a big empty space in the middle. Every time you want to show a different picture, you just swap the picture in the middle — you never throw away the frame! This file IS that frame. It's the one-and-only HTML page that your browser ever loads. All the "pages" you see (Home, Browse, etc.) are really just different pictures being slotted into the middle of this frame by JavaScript.

Core Responsibilities

  • SPA Shell: Serves as the single, persistent HTML document; the browser never performs a full-page navigation away from this file.
  • Asset Pipeline Bootstrap: Loads every external resource the application needs — fonts, design-token CSS, component CSS, page-specific CSS, and the favicon — in the correct dependency order.
  • Persistent Chrome: Renders the navigation bar (<nav>) and footer (<footer>) once; they survive all client-side route transitions.
  • Content Mount Point: Provides <main id="app"> as the sole DOM node the client-side router targets for injecting/swapping page content.
  • Script Orchestration: Loads five JavaScript modules (i18n, banner, home, browse, router) in dependency order at the bottom of <body> so the DOM is fully parsed before any script executes.
  • Internationalization (i18n) Hooks: Sprinkles data-i18n attributes on translatable text nodes so the i18n module can find and replace them at runtime.
  • Progressive Enhancement of Language Toggle: Embeds an inline SVG globe icon inside #langBtn so the language-switch button is immediately styled without waiting for an icon font or sprite sheet.

Block 1 — DOCTYPE Declaration

🎯 Purpose: Forces the browser into standards mode so every CSS box-model calculation, layout algorithm, and rendering behaviour follows the W3C specification rather than legacy "quirks mode" heuristics.

🧒 ELI5: It's like telling the referee "we're playing by the official rules" before the game starts, so nobody argues about what's fair.

⚙️ Technical Details: <!doctype html> is the shortest valid doctype for HTML5+. It carries no version number or DTD URI because HTML is now a "living standard." Without it, Internet Explorer and some older engines fall back to quirks mode where width includes padding+border (IE5 box model), percentage heights resolve differently, and <table> font inheritance breaks.

📥 Inputs: None — this is a parser directive, not a DOM element.

📤 Outputs: Browser rendering mode set to "no-quirks."

💻 Actual Code:

<!doctype html>

─────────────────────────────────────────────────────────────────────────────

Block 2 — <html> Root Element

🎯 Purpose: Establishes the document's language (en) and text direction (ltr), informing screen readers, search engines, and CSS logical properties how to interpret and render content.

🧒 ELI5: This is the big box that holds everything. The labels on the box say "English" and "read left-to-right" so everyone knows which way to read.

⚙️ Technical Details:

  • lang="en" enables correct hyphenation (hyphens: auto), tells assistive technologies which speech-synthesis profile to load, and helps Google determine the page's primary language.
  • dir="ltr" sets the base directionality for the Unicode Bidirectional Algorithm (UBA). When the i18n module switches to Farsi, it can flip this to dir="rtl", which cascades to every descendant via CSS logical properties (margin-inline-start, etc.).

📥 Inputs: None.

📤 Outputs: Root element available to all scripts as document.documentElement.

🔗 Dependencies: The i18n.js module reads and mutates both lang and dir at runtime.

💻 Actual Code:

<html lang="en" dir="ltr">

Block 3 — <head> Element (Container)

🎯 Purpose: Houses all metadata, style, and resource-hint declarations that the browser must process before it can begin layout and paint.

🧒 ELI5: Think of <head> as the instruction manual you read BEFORE you start building your LEGO set. It doesn't show you the LEGO pieces (that's <body>), but it tells you what tools and stickers you'll need.

⚙️ Technical Details: Everything inside <head> is non-visual. The browser constructs a parallel CSSOM (CSS Object Model) from the stylesheets listed here. Rendering is blocked until all render-critical CSS is downloaded and parsed. The <head> is parsed sequentially, which is why resource hints (preconnect) precede the actual font <link>.

📥 Inputs: None (opening tag).

📤 Outputs: Fully configured CSSOM, document title, favicon, and preconnected sockets.

💻 Actual Code:

<head>

─────────────────────────────────────────────────────────────────────────────

Block 4 — Meta Charset Declaration

🎯 Purpose: Declares the character encoding as UTF-8, ensuring every glyph — from English letters to Farsi script (وزیرمتن) to emoji (☁️) — decodes correctly.

🧒 ELI5: This tells the browser which alphabet book to use. UTF-8 is the alphabet book that knows ALL the languages in the world, plus smiley faces!

⚙️ Technical Details: The HTML spec requires this meta tag to appear within the first 1024 bytes of the document. If absent or declared late, the browser performs encoding sniffing, which can cause a re-parse of the entire document and potential XSS vulnerabilities via charset mismatch attacks (e.g., UTF-7 injection).

📥 Inputs: None.

📤 Outputs: document.characterSet === "UTF-8".

💻 Actual Code:

<meta charset="utf-8" />

Block 5 — Meta Viewport Configuration

🎯 Purpose: Instructs mobile browsers to set the layout viewport width to the device's screen width and the initial zoom level to 100%, enabling responsive design.

🧒 ELI5: Without this, your phone would try to show the entire website shrunk down to a tiny size like looking at a poster through binoculars held backwards. This tag says "show it at normal size, please!"

⚙️ Technical Details:

  • width=device-width maps the CSS px unit to the device-independent pixel (DIP) grid, making media queries like @media (max-width: 768px) fire at the expected breakpoints.
  • initial-scale=1 prevents iOS Safari from zooming out on landscape rotation. Note: maximum-scale=1 and user-scalable=no are intentionally omitted to preserve accessibility (pinch-to-zoom).

📥 Inputs: None.

📤 Outputs: window.innerWidth matches CSS media query widths.

💻 Actual Code:

<meta name="viewport" content="width=device-width, initial-scale=1" />

Block 7 — Preconnect to Google Fonts API

🎯 Purpose: Opens an early TCP+TLS connection to fonts.googleapis.com so that when the browser encounters the font stylesheet <link>, the handshake is already complete, shaving 100–300 ms off font load time.

🧒 ELI5: Imagine you're ordering pizza. This step is like calling the pizza place ahead of time and saying "get the oven hot!" — so when you actually order, the pizza comes faster.

⚙️ Technical Details: rel="preconnect" performs DNS resolution, TCP handshake, and TLS negotiation. This is a non-blocking resource hint; if the connection isn't used within ~10 seconds, the browser may close it. This link targets the API server that returns the @font-face CSS, NOT the server that hosts the actual font binary files (that's fonts.gstatic.com, handled next).

📥 Inputs: None (resource hint).

📤 Outputs: A warm socket to fonts.googleapis.com.

💻 Actual Code:

<link rel="preconnect" href="https://fonts.googleapis.com">

─────────────────────────────────────────────────────────────────────────────

Block 8 — Preconnect to Google Fonts Static CDN

🎯 Purpose: Opens an early TCP+TLS connection to fonts.gstatic.com — the CDN that serves the actual WOFF2/TTF binary font files. The crossorigin attribute is mandatory here because font files are fetched with CORS.

🧒 ELI5: The first call went to the pizza restaurant's phone line (Google API). This second call goes to the delivery driver's garage (Google Static) so he can start his car early.

⚙️ Technical Details: Without crossorigin, the browser opens a non-credentialed connection, but fonts are always fetched as anonymous CORS requests. This mismatch means the preconnected socket can't be reused, and the browser opens a second connection anyway — wasting the preconnect entirely. The crossorigin attribute (equivalent to crossorigin="anonymous") ensures the connection's credential mode matches the font fetch.

📥 Inputs: None (resource hint).

📤 Outputs: A warm, CORS-compatible socket to fonts.gstatic.com.

💻 Actual Code:

<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

Block 9 — Google Fonts Stylesheet

🎯 Purpose: Fetches a dynamically generated CSS file from Google that contains @font-face declarations for four font families at the specified weight ranges, giving the application its distinctive typographic identity.

🧒 ELI5: This is like going to the sticker store and picking out four different fancy letter styles: one for titles, one for normal reading, one for Farsi text, and one for special headings.

⚙️ Technical Details:

Font Family Weight Range Purpose
Manrope 400–800 Primary sans-serif for body copy. Variable font, so a single file covers Regular through ExtraBold.
Cinzel 400–700 Decorative serif for brand/hero headings.
Vazirmatn 300–700 Persian/Arabic script support for RTL i18n.
Sora 400, 500, 600 Secondary geometric sans-serif, likely used for UI controls.

display=swap sets font-display: swap in every generated @font-face, meaning text is painted immediately with a fallback font and re-rendered once the web font arrives (FOUT rather than FOIT). This is optimal for Core Web Vitals (Largest Contentful Paint).

📥 Inputs: Preconnected sockets from Blocks 7 & 8.

📤 Outputs: Four font families available in the CSSOM; text renders with font-family: 'Manrope', … etc.

🔗 Dependencies: Consumed by tokens.css (custom properties like --font-body), which is loaded next.

💻 Actual Code:

<link href="https://fonts.googleapis.com/css2?family=Manrope:wght@400..800&family=Cinzel:wght@400..700&family=Vazirmatn:wght@300..700&family=Sora:wght@400;500;600&display=swap" rel="stylesheet">

Block 10 — Design Tokens Stylesheet

🎯 Purpose: Loads tokens.css, a file containing CSS custom properties (variables) that define the design system's primitive values: colours, spacing scale, font stacks, border radii, shadows, and breakpoints.

🧒 ELI5: This is the box of crayons. Before you draw anything, you pick which colours you'll use. tokens.css is where all the colour names live, like --color-primary (the blue crayon) and --space-4 (four steps wide).

⚙️ Technical Details: By loading tokens first, every subsequent stylesheet can reference var(--token-name) without worrying about cascade order. This follows the Design Token → Base → Components → Pages layering convention used by systems like Salesforce Lightning and IBM Carbon.

📥 Inputs: Font families from Google Fonts (Block 9) — tokens likely map --font-body: 'Manrope', sans-serif.

📤 Outputs: Custom properties on :root available to all downstream CSS.

🔗 Dependencies: Consumed by base.css, components.css, home.css, browse.css.

💻 Actual Code:

<link rel="stylesheet" href="/assets/css/tokens.css">

Block 19 — Navigation Bar

🎯 Purpose: Renders the persistent top navigation containing the logo, brand name, subtitle, external website link, and language toggle button. This element is never destroyed by the SPA router.

🧒 ELI5: This is the roof of our house — it's always there, no matter which room (page) you're standing in. It has the family name sign (logo), a doorbell to the main website, and a magic button that changes the language.

⚙️ Technical Details:

  • <nav class="nav"> — Semantic landmark element; assistive tech exposes it as a navigation role. The .nav class hooks into components.css for visual styling (backdrop blur, sticky positioning, z-index).

  • <img src="/assets/icon/logo.png" alt="CloudAvid"> — Company logo image. The alt text ensures screen readers announce the brand name.
  • <div class="nav-logo-text"> — Stacks brand name and subtitle vertically beside the logo image.

Block 20 — Main Content Mount Point

🎯 Purpose: This empty <main> element is the sole injection target for the client-side router. Every route handler renders its HTML string into document.getElementById('app').innerHTML.

🧒 ELI5: This is the blank canvas in the middle of the picture frame. The robot painter (JavaScript router) keeps drawing new pictures on it every time you click a link, but the frame never moves.

⚙️ Technical Details:

  • <main> is a semantic landmark that assistive tech exposes as the document's primary content region. There should be only one <main> per document (spec recommendation).
  • id="app" is the contract between index.html and router.js. The router performs document.getElementById('app') to locate this node.
  • The element starts empty in the HTML source. Content appears only after router.js executes and matches the current URL to a route handler (e.g., home.js's render() or browse.js's render()).
  • Because the router replaces innerHTML, any event listeners attached to children of #app must either be re-attached after each render or use event delegation on #app itself.

📥 Inputs: Rendered HTML from home.js, browse.js, or banner.js.

📤 Outputs: Visible page content between nav and footer.

🔗 Dependencies: router.js (write), home.js (content), browse.js (content), banner.js (content).

💻 Actual Code:

<!-- MAIN CONTENT — this is the only part that changes -->
<main id="app"></main>
